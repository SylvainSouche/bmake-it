# Real mkmk separates a build-time file tree from a run-time file tree; non-source runtime data (icons, message files, etc.) lives in per-framework, optionally per-OS-specific directories and is copied or symlinked into a consolidated run-time view by a dedicated command

Runtime-only assets are kept in framework-level directories, with an optional OS-specific variant directory per asset directory (falls back hierarchically: exact OS match, then OS family, then a generic default). A dedicated command consolidates these into a single runtime view (via copy or symlink) that the running application actually uses -- the running app never reads the build-time tree directly. This directly informs REQ-module-resource-files: real mkmk's resource model is framework-level (not module-level as tentatively assumed), supports per-OS variants, and requires a separate 'materialize runtime view' step rather than resources landing directly next to the binary at build time. Needs a decision on how much of this we adopt.
