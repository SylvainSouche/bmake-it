# Same-turn testing of the DLL (shared-lib, LIB_SHARED=YES default) path with TOOLCHAIN=msvc found a genuine gap distinct from any wrapper bug: cl.exe/link.exe compiled greet.c and linked greet.dll successfully (confirmed via file(1) and the .dll existing on disk), but produced NO import library (greet.lib) despite /IMPLIB: being correctly passed -- because greet.c, written in a portable/Unix-idiom style with no __declspec(dllexport) markup, exports zero symbols under MSVC's model. Unlike gcc/clang(-mingw), which export every global symbol from a DLL by default (matching Unix .so/.dylib behavior, confirmed working via the Cygwin-gcc test the same session), MSVC/link.exe require EXPLICIT dllexport annotation (or a .def file, or /EXPORT: on the link line) for any symbol to appear in the DLL's import library. rade-bmake's current shared-library convention (plain portable C, no annotations, matching the gcc/clang-mingw default-export model) does not work out of the box for TOOLCHAIN=msvc's shared-lib case; the static-lib case (LIB_SHARED=NO) is unaffected since static archives have no export/visibility concept and was confirmed fully working
