# mk.toolchain.llvm.mk and mk.toolchain.gcc.mk detect the compiler via a single hardcoded absolute path (exists(/usr/bin/clang), exists(/usr/bin/gcc)) rather than a PATH search, so on any system where the compiler lives elsewhere (pkgsrc's /usr/pkg/bin, MacPorts' /opt/local/bin, Homebrew, etc.) TOOLCHAIN=llvm silently falls back to whatever plain cc happens to be, with no warning that the requested toolchain was not actually used

Confirmed empirically: NetBSD's pkgsrc clang-21.1.8 installs to /usr/pkg/bin/clang, not /usr/bin/clang. With TOOLCHAIN=llvm explicitly set and clang genuinely on PATH, 'bmake -V CC' still resolved to 'cc' -- on this NetBSD build, 'cc' and 'gcc' are the same hardlinked binary (GCC 10.5.0), so the user asked for llvm and silently got gcc instead. The failure is silent: no error, no warning, mk.toolchain.llvm.mk's .if exists(/usr/bin/clang) simply evaluates false and falls through to the plain-cc branch.

Same root cause and same fix shape as the earlier self-reentrancy finding (nested-invocation-reentrancy-guard-req): a hardcoded absolute path standing in for what should be a PATH-based lookup. mk.toolchain.gcc.mk has the identical exists(/usr/bin/gcc) pattern and is presumed to have the same failure mode on a system where gcc is installed but not at that exact path (not yet independently reproduced, since the systems tested so far happen to have gcc at /usr/bin/gcc).
