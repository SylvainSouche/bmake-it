# Investigated portable bmakes own mk-bmake (generic pmake) and mk-netbsd (NetBSD) file sets in addition to FreeBSD share/mk: confirmed cross-compilation is an EXTERNAL orchestration pattern across the entire bsd-make family, not something any variant of bsd.prog.mk/bsd.lib.mk implements internally. Also confirmed no variant auto-creates install destination directories

Extends OBS-validation-target-arch-inert-without-basesystem. Checked mk-bmake (generic portable pmake files: compiler.mk detects compiler TYPE via CC --version parsing, not target selection; target-flags.mk is for per-object-file flag overrides, unrelated to cross-arch targeting; host-target.mk only detects the HOST platform) and mk-netbsd (NetBSD's own bsd.own.mk: MACHINE/MACHINE_ARCH are used purely as DATA for architecture-specific branching -- CPU quirks, conditional flags -- never as a trigger that auto-selects a cross-compiler binary). Conclusion, consistent across FreeBSD, NetBSD, and generic pmake: real cross-compilation always happens via an EXTERNAL wrapper/orchestration layer outside bsd.prog.mk/bsd.lib.mk themselves -- NetBSDs build.sh builds a full cross-toolchain into  first, then invokes bmake with CC=/bin/<target-triple>-gcc explicitly set on the command line; FreeBSDs Makefile.inc1 does the analogous thing for buildworld. In both cases, TARGET/TARGET_ARCH-style variables are DATA that individual .mk files consult for architecture-specific decisions, not a switch bsd.prog.mk/bsd.lib.mk use to look up a compiler themselves. Separately confirmed: neither mk-netbsd nor FreeBSD share/mk auto-creates missing DESTDIR parent directories during install -- both assume a pre-populated destination hierarchy (traditionally via a separate mtree step), consistent across the whole family, not a FreeBSD-specific quirk.
