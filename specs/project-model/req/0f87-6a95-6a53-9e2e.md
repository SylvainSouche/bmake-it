# Any build-system mechanism that shells out to a nested make invocation to perform discovery or dependency-order analysis (module discovery, framework discovery, LIBS=/PREREQS= topological ordering) must guard against self-reentrant and concurrent re-invocation: the invoked make binary must be resolved to an absolute path, never a bare name looked up via PATH, and any cache file the mechanism writes must not be unconditionally deleted-and-regenerated in a way that races a concurrent or nested invocation of the same discovery for the same directory

Concretely, for the current implementation: gen-mod-order.sh and gen-fw-order.sh must resolve their own $BMAKE to an absolute path before invoking it (mirroring the fix already applied to tests/harness/run-tests.sh's wrapper generation), and mk.framework.mk/mk.workspace.mk's discovery steps must not blindly 'rm -f <cache> && regenerate' on every parse -- at minimum this should be skipped when a fresh cache already exists for the current parse, and ideally guarded against concurrent regeneration (e.g. a lock file, or writing to a temp file and renaming atomically into place).

Why this is a REQ and not just a bugfix note: the failure mode is a property of the mechanism (shelling out to a nested instance of the same build tool for discovery/analysis), and it recurs everywhere that pattern is used -- it was found once, in module/framework discovery, but the same shape of risk applies to any future dependency-analysis mechanism built the same way (e.g. the deferred order-cache-auto-triggered-req 'make order' mechanism). Recording it as a requirement on the mechanism class means future implementations of that class are checked against it, not just the two scripts that happened to be examined.
