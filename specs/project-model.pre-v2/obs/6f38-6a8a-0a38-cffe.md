# Linux targets also have a libc choice (glibc vs musl, primarily), parallel to the win ABI question -- another potential axis beyond os-arch-toolchain, deferred along with the rest of Linux-specific scope

User correctly noted that Linux targets are not fully homogeneous either: glibc (the standard GNU libc, used by most mainstream distros) and musl (used by Alpine and commonly chosen for fully static, minimal, highly portable binaries) are both realistic choices, with real consequences for static-linking ability and portability across distros -- other libc variants (uClibc, bionic, etc.) exist but are far more niche. This directly parallels the win-target ABI discussion (OBS-win-target-has-three-abi-flavors): a single os label (linux) may not be enough on its own, the same way win alone was not enough, if libc choice matters to a given build. Unlike win, however, Linux is not part of REQ-phase1-concrete-targets at all, and REQ-os-label-set-req already defers per-distro Linux handling -- libc choice is a closely related facet of that same deferred area, not a new decision needed now. Recorded as context so this does not need to be rediscovered when Linux support is actually designed.
