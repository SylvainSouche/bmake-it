# win targets have three distinct possible ABI/runtime flavors (MinGW, Cygwin, MSVC), unlike every other OS in the model which has one canonical ABI -- the win target key may eventually need a 4th slot, not just os-arch-toolchain

Following on from REQ-win-target-via-cross-toolchain-req and OBS-cygwin-native-vs-mingw-cross-are-separate-packages, user correctly synthesized that a win target can actually be produced with three genuinely distinct ABIs/runtimes, all reachable from a Linux-like host (WSL or Cygwin): (1) MinGW ABI, via a mingw-w64 cross-compiler (gcc or clang/clang-cl), no cygwin1.dll or MSVC runtime dependency, buildable from nearly any host; (2) Cygwin ABI, via Cygwins own native gcc, depends on cygwin1.dll, realistically only meaningful when actually running inside Cygwin; (3) MSVC ABI, via clang-cl targeting the real Windows SDK/MSVC headers and import libraries (e.g. using a tool like xwin to fetch/repackage those for cross-building from Linux) -- the least trivial of the three to set up for cross-compilation. Every other OS in the current model (macos, freebsd, linux) has exactly one canonical ABI, so the existing target key (<os>-<arch>-<toolchain>, REQ-target-key-includes-toolchain) is sufficient for them. win may be the one case that needs a 4th slot in the key (ABI/runtime), not just a toolchain choice -- not yet designed, deferred along with the rest of the win target work (win is not in REQ-phase1-concrete-targets). Recorded as pure context to inform whatever future work brings win into scope, so this doesnt need to be rediscovered.
