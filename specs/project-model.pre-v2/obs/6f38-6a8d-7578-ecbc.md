# Empirically confirmed: real bsd.lib.mk has no LIB_SHARED=YES|NO toggle at all. LIB alone always triggers a static .a; SHLIB_MAJOR presence ADDITIONALLY triggers a shared .so -- both build simultaneously, not either/or

Test performed: built a minimal library module (LIB=greet SRCS=greet.c SHLIB_MAJOR=1, .include <bsd.lib.mk>) against real FreeBSD share/mk. Result: BOTH libgreet.a (static archive) and libgreet.so.1 (shared, versioned) were produced, with the libgreet.so -> libgreet.so.1 symlink chain exactly as expected -- but as a SIMULTANEOUS, automatic consequence of LIB+SHLIB_MAJOR both being set, not via any LIB_SHARED switch, which does not exist anywhere in bsd.lib.mk source. Source inspection confirms: defined(LIB) alone unconditionally builds the static lib.a; defined(SHLIB_NAME) (itself gated on defined(SHLIB_MAJOR)) additionally builds the shared library. No native mechanism was found to suppress the static .a while keeping only the shared .so. This CONFIRMS the exact risk flagged as Tier 1.2 in the validation plan. Consequence for the design: REQ-lib-shared-defaults-yes-req and REQ-lib-shared-no-is-static-req, both currently classified as reusing a native bsd.lib.mk mechanism, are factually wrong on that point and need correction -- see the superseding REQ.
