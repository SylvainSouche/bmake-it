# Compiler-native -MD dependency tracking is confirmed to work automatically ONLY when using FreeBSD's own actual bsd.sys.mk (e.g. on a real FreeBSD host's native /usr/share/mk); it is confirmed ABSENT from NetBSD's own bundled mk set. Whether MacPorts' bsdmake (a phase-1 target host) includes it is unverified and must be checked on a real Mac before relying on it there

Scopes REQ-compiler-native-dependency-tracking-req correctly: its confirmed-working claim applies specifically to FreeBSD hosts using FreeBSDs own native share/mk unchanged, not to the BSD-make family in general. Confirmed ABSENT in NetBSDs own bundled mk-netbsd set (zero -MD wiring, zero rebuild on header change). For macOS (a phase-1 host, REQ-phase1-concrete-targets), whether MacPorts own bsdmake port includes equivalent -MD wiring in its own bsd.sys.mk is UNKNOWN -- genuinely untestable without a real Mac (same gap as Tier 1.3 in spec/60-bsd-make-validation-plan.md, now understood to cover this too, not just Mach-O dylib versioning). Design consequence: mk.prog.mk/mk.lib.mk should not assume -MD-based dependency tracking is inherited for free on every phase-1 target. If MacPorts bsdmake turns out to lack it, the fallback is straightforward -- mk.prog.mk/mk.lib.mk can add -MD -MF<generated-path> to CFLAGS/CXXFLAGS themselves and .include the resulting per-object files, replicating what FreeBSDs bsd.sys.mk already does, rather than needing mkdep or any more complex mechanism.
