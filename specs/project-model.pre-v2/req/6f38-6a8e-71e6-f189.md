# mk.toolchain.<name>.mk must explicitly set CC/CXX/LD/AR/AS to concrete cross-compiler paths/binaries based on TARGET/TARGET_ARCH/TOOLCHAIN, following the same external-orchestration pattern every bsd-make lineage (FreeBSD Makefile.inc1, NetBSD build.sh) uses -- TARGET/TARGET_ARCH cannot be passed through to bsd.prog.mk/bsd.lib.mk expecting them to select a compiler themselves

Gives concrete design guidance following REQ-target-arch-toolchain-selection-is-custom-req and OBS-validation-cross-compile-is-external-orchestration-everywhere: mk.toolchain.<name>.mk (REQ-toolchain-triggers-dedicated-mk-file-req) needs its own explicit lookup/naming-convention logic mapping (TARGET, TARGET_ARCH, TOOLCHAIN) combinations to real compiler binary paths (e.g. a triple-based naming convention like <target_arch>-<target>-clang, or an explicit lookup table), and set CC/CXX/LD/AR/AS to those concrete paths directly -- mirroring exactly how NetBSDs build.sh and FreeBSDs Makefile.inc1 do it for their own base-system builds, just scoped to this projects own phase-1 target set (REQ-phase1-concrete-targets) rather than a whole OS source tree. TARGET/TARGET_ARCH remain available as plain data variables for any architecture-conditional logic elsewhere in the mk.*.mk files, following the same pattern as NetBSDs MACHINE/MACHINE_ARCH usage, but they do not themselves trigger compiler selection -- that responsibility belongs entirely to mk.toolchain.<name>.mk.
