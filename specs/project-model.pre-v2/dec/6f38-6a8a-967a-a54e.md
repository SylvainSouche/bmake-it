# Header lookup for a PREREQS-declared framework reads directly from that frameworks own include/ (source), never from any build/<KEY>/ output; matches real mkmk, which never touches build output for headers

User raised a genuine fork while describing workspace-level build flow: should header lookup for a prereq framework read from (a) the prereq frameworks own include/ source directory, (b) a per-target build/<KEY>/include/ staged copy at framework level, or (c) a workspace-wide consolidated build/<KEY>/include/? User themselves noted real mkmk never looks at build output for headers at all -- it reads PublicInterfaces/PublicGenerated directly. Agreed and confirmed option (a): headers are plain text and generally do not need per-target staging the way compiled .o/.so artifacts do; staging them would add an unnecessary copy step and a new ordering dependency (headers would need staging to complete before any dependent module could compile, unlike the current model where lib/bin staging only needs to happen before OTHER modules link against them, not before headers can be read). A workspace-wide consolidated include/ would also be actively wrong: it would erase which framework a header came from, undermining the whole point of PREREQS-based visibility (REQ-three-level-header-visibility-req).
