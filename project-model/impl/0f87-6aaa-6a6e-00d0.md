# mk.framework.mk _build_modules / mk.workspace.mk _build_frameworks: each module/framework's build output tee'd to build.log unconditionally; a failure touches build.failed and continues to the next one unless FAIL_FAST=yes; mk.workspace.mk's all: target generates build-report/index.html from those markers when REPORT=yes

Extended 2026-09-16, two real gaps found by tracing the
integration-manager-ci-cycle use case through to its conclusion rather
than stopping at "it works once":

- **Target-key collision**: `build-report/`/`test-report/` were flat at
  the workspace root, keyed only by `RUN_ID`. Two target keys (e.g.
  `TOOLCHAIN=llvm` and `TOOLCHAIN=gcc`) built under the same `RUN_ID` to
  correlate them as one CI pass would silently overwrite each other's
  dashboard -- exactly the scenario `RUN_ID=` exists to support. Fixed:
  both dashboards now live under `<REPORT_DIR>/<RUN_ID>/<KEY>/`, and
  `latest/<KEY>/` is updated per-key rather than wiping the whole
  `latest/` tree.
- **`clean` never removed the dashboards at all**: workspace `clean`
  cleaned `build/`/`distrib/` but had no knowledge that
  `build-report/`/`test-report/` existed. Fixed: `TARGET=all clean`
  removes both trees entirely; a plain `clean` removes only the current
  target key's data (`<REPORT_DIR>/*/<KEY>/`, across every `RUN_ID` and
  `latest/`) and prunes any run directory left empty by that removal,
  leaving other target keys' history untouched -- matching the existing
  this-target-only-vs-TARGET=all distinction `clean` already has for
  `build/`.
