# Add <phase>.${TARGET}_${TARGET_ARCH}.mk to the hook cascade, checked after <phase>.${TARGET}.mk; no combined toolchain+target_arch filename is added

Naming matches share/<os>_<arch>'s existing convention, not a new pattern. No full-key (target+arch+toolchain) variant: the realistic need (an external prefix that differs by arch on one OS) is fully covered by target_arch alone, and the existing separate .${TOOLCHAIN}.mk variant already covers toolchain-specific overrides independently -- combining both into one filename would be combinatorial (target x arch x toolchain) for a case with no concrete motivating example. Cascade order: .mk, .${TOOLCHAIN}.mk, .${TARGET}.mk, .${TARGET}_${TARGET_ARCH}.mk -- general to specific, ALL matching levels included (unchanged cascade philosophy), not just the most specific.
