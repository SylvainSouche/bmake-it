# Every mechanism that shells out to a nested make invocation for discovery or dependency-order analysis must guard against self-reentrant and concurrent re-invocation, as a general architectural rule -- not a one-off fix to the one instance found

The user's direction: this class of risk (module discovery, dependency/order analysis) is inherently self-reentrant-prone whenever it shells out to a nested instance of the same tool, and the spec must guard against that generally rather than only patching the specific test-harness incident. Two concrete guards follow from the observation: (1) any nested invocation of the make binary from a helper script must use an absolute path, never a bare command name resolved via PATH, since PATH can resolve back to a wrapper or the invoking process's own name; (2) discovery/order-generation caches must not be unconditionally deleted-then-regenerated on every parse with no guard, since nested or concurrent invocations of the same directory's discovery can race on that file. This is recorded as a requirement on the mechanism class (module discovery, framework discovery, LIBS=/PREREQS= dependency-order analysis), not as an implementation-note fix to gen-mod-order.sh/gen-fw-order.sh alone.
