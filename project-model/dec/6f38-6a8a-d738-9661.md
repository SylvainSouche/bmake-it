# Sibling-module ordering within a framework applies ONLY to the link step of modules whose LIBS= names another sibling module; compilation of every module is order-independent, since headers never come from sibling modules

User clarified/narrowed the framework-level ordering logic (REQ-framework-build-order-follows-prereqs-graph-req) when applied one level down to sibling modules within a single framework: it does NOT apply the same way, because LIBS= is purely a link-time (-l) concern (REQ-libs-macro-link-only-headers-via-prereqs-req) -- header resolution (-I) is entirely managed by the frameworks PREREQS (REQ-headers-resolved-from-source-req, REQ-generated-headers-in-build-tree-req), never by a modules LIBS= list. Consequence: compiling any module (src/ -> obj/) never depends on any sibling module having built first, since nothing about compilation reads from a sibling modules output -- all modules in a framework can compile in any order, fully in parallel. The only real ordering constraint is at the LINK step: a module that lists a sibling module in LIBS= cannot complete its link step until that sibling has already produced its own linked artifact. This is a narrower, link-step-scoped ordering requirement, not a whole-module build-order requirement the way framework-level PREREQS is.
