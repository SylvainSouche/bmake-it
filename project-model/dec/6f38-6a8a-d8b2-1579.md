# Build strategy is fused compile+link per module/framework (bsd.*.mk-idiomatic), not global compile-all-then-link-all phases; a dependency (sibling module via LIBS, or any module/framework supplying a consumed promoted-generated header) must be FULLY built before its dependent starts, since generated+promoted headers create a real compile-time dependency, not just links link-time one

User chose the fused per-module build strategy over global compile-all/link-all phases, matching real bsd.*.mk idiom (each directorys make invocation compiles and links its own target in one pass; cross-module/cross-framework ordering is achieved purely through directory-descent order). User also pointed out this interacts with generated headers: since a module can consume a SIBLINGs promoted-public generated header via the frameworks build/<KEY>/include/ (REQ-generated-headers-in-build-tree-req, REQ-incl-macro-promotes-generated-headers-req), that sibling must have already run ITS OWN header generation and promotion step before THIS module can even compile -- this is a genuine compile-time dependency, not merely a link-time one. This means REQ-sibling-module-ordering-link-only-req (compilation is fully order-independent, only linking is ordering-constrained) was too broad -- it is superseded by a fuller model: whenever module/framework X depends on module/framework Y for EITHER a consumed promoted-generated header OR a link-time library, Y must be FULLY built (through its own generation, promotion, compilation, and linking) before X starts building at all. The fused-per-module strategy handles both dependency kinds with one mechanism (full-build-before-dependent), which is simpler than trying to separate compile-only and link-only ordering.
