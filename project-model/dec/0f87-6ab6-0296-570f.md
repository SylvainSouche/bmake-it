# A framework may declare PUBLIC_HEADERS_SYSTEM=yes in its own makefile; any consumer's PREREQS=-driven include of that framework's public headers then uses -isystem instead of -I, suppressing warnings that originate from those headers without touching the consumer's own -Wall -Wextra

Framework-level opt-in, independent of any individual module's own WARN= setting -- the framework maintainer decides its whole public header surface should be treated as system headers by consumers, typically because the framework wraps or vendors third-party code (item 7's own vendored-code motivation). Deliberately not inferred automatically from whether any module inside uses WARN=none: that would require correlating module-level and framework-level state for no real benefit -- an explicit framework-level flag is simpler and matches how PREREQS= itself is already an explicit, framework-level declaration, not inferred from module contents.

Only affects the cross-framework PREREQS= case (a consumer in a DIFFERENT framework); a module's own sibling-module include of its OWN framework's public headers (same-framework, not PREREQS-driven) is unaffected -- D3's own question was specifically about "a framework" exposing headers to the outside, matching the existing PREREQS=-is-the-visibility-boundary design (20-headers-and-linking.md).
