# OPENMP=yes probes real -fopenmp compiler acceptance (gcc/clang) before using it, adds MacPorts' own libomp path explicitly when it exists on disk (belt-and-suspenders -- empirically found unnecessary on this exact MacPorts LLVM 22 install, whose own driver already bakes those paths in for -fopenmp, but not guaranteed for every LLVM package/version or a different macOS package manager), and .errors if requested but unsupported

Empirical finding worth recording precisely: on this host (MacPorts clang 22, /opt/local/bin/clang -> /opt/local/libexec/llvm-22/bin/clang), a bare -fopenmp already resolves libomp correctly with ZERO explicit -I/-L needed -- confirmed via `clang -fopenmp -### ...`, which shows the driver itself injecting `-I/opt/local/include/libomp` and `-L/opt/local/lib/libomp -lomp` automatically. This is MacPorts' own LLVM package configuration, not generic clang behavior -- Apple's Xcode clang has no such wiring (it doesn't bundle libomp support the same way), and Homebrew's own LLVM package's defaults were not checked (not installed on this host). Adding the explicit MacPorts path anyway when it exists on disk is redundant-but-harmless on this exact host and a genuine safety net for a differently-configured MacPorts LLVM version or a future toolchain where the auto-wiring isn't present -- not blindly copying the brief's own assumption without checking it first.

Probe: a bare `-fopenmp` compile-only invocation (no #include, no pragma) against a trivial empty main, checking the COMPILE exit code -- confirms the flag itself is accepted, not a full functional link+run (that's what the harness test case does separately, for real). Skipped for TOOLCHAIN=msvc: cl.exe's own OpenMP support (/openmp, added via a new msvc-cc-wrapper.sh case translating -fopenmp) has been stable for a very long time; assumed present rather than probed, since a Cygwin-hosted MSVC probe couldn't be verified from this host either way.
