# Testing Bmake It against multiple macOS package-manager toolchains (MacPorts/Homebrew/pkgsrc-pkgin/Nix) does not need one VM per manager -- they're userland installs to different prefixes on the same macOS kernel, coexisting fine on one system (that's what _TOOL_PREFIXES already relies on). The single already-planned macos_arm64 tart VM gets all four installed side by side; the harness selects which one a given test run exercises by pointing _TOOL_PREFIXES/environment at that manager's own prefix, not by provisioning separate VMs

Genuinely different from OS-level test-matrix sandboxing (FreeBSD/NetBSD/Linux need separate VMs/containers -- different kernels). Docker doesn't apply here at all -- Docker for Mac only runs Linux containers, it cannot containerize macOS. This is specifically about avoiding a likely over-engineering mistake: assuming package-manager testing needs the same 'one VM per target' multiplication that OS-level testing does.
