# Generated headers (lex/yacc, other tooling) are a build-time artifact, not source: private ones live in module build/<KEY>/include/; modules can explicitly promote some to public, copied up to a framework-level build/<KEY>/include/ containing ONLY generated headers; workspace-level build/<KEY>/include/ is never used for compilation, only for packaging/install

Refines REQ-headers-resolved-from-source-req with an explicit, scoped exception for generated headers (e.g. lex/yacc output, or other codegen tooling per REQ-supported-languages). Unlike hand-written headers, generated headers do not exist until the build runs, so they cannot live in a source include/ directory. Confirmed model: (1) by default, a modules generated headers are private, landing in module/build/<KEY>/include/, visible only to that modules own compilation; (2) a module can explicitly declare specific generated headers as public (mechanism/macro name not yet decided); on module build, those get copied up into framework/build/<KEY>/include/, a framework-level directory that holds ONLY generated headers promoted this way -- never hand-written source headers, which continue to live in fw/include/ per REQ-headers-resolved-from-source-req; (3) when another framework resolves a PREREQS-declared frameworks headers, it must search BOTH that frameworks fw/include/ (hand-written, source) AND its build/<KEY>/include/ (promoted generated) to see the complete public header set -- build/<KEY>/include/ IS consulted here, a deliberate, scoped exception to the general never-consult-build-for-headers rule; (4) there is no workspace-level build/<KEY>/include/ used during compilation at all -- a workspace-wide header consolidation only happens as part of packaging/install (REQ-packaging-per-format-targets-req), a distinct concern from build-time header resolution.
