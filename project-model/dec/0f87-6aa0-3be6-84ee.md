# The test harness must cover every feature of the system, not just isolated bsd-make mechanics: including actually running the built program (not just checking it compiled/linked) and verifying link resolution actually worked, for both nominal and error cases

User specified the test harness scope must expand from the initial small prototype (which each tested one isolated bsd-make mechanic) to comprehensive coverage of every system feature: workspace/framework/module discovery, PREREQS/LIBS resolution, header visibility, resource staging, versioned libraries, packaging, CLI variables, convenience targets, and so on. Critically, coverage must include RUNTIME verification -- actually executing the built program (not merely confirming compilation and linking succeeded) -- and explicit verification that LINK RESOLUTION worked correctly (the right libraries were found and linked). Both NOMINAL cases (expected-success scenarios) and ERROR cases (expected-failure scenarios, verifying graceful diagnostics) must be covered.
