# Select the final link driver per module: ${CXX} when SRCS contains a C++ source, or LINK_CXX=yes is set explicitly; ${CC} otherwise

Mirrors real bsd.init.mk's own _CCLINK mechanism (confirmed by reading /opt/local/share/mk/bsd.init.mk on this MacPorts host: `.if defined(PROG_CXX) || <SRCS matches a C++ suffix> ... _CCLINK ?= ${CXX} ... _CCLINK ?= ${CC}`), not copied verbatim since Bmake It never .includes bsd.init.mk/bsd.prog.mk/bsd.lib.mk at all (confirmed: mk.prog.mk/mk.lib.mk only .include Bmake It's own mk.*.mk role files) -- the logic is reimplemented as Bmake It's own internal _CCLINK variable.

Naming diverges from bsd.prog.mk's PROG_CXX= deliberately: PROG_CXX means "use this name instead of PROG=", a different concept Bmake It's PROG=/LIB= macros don't need. The explicit override is named LINK_CXX=yes instead, for the one case auto-detection can't see: a C-only module (e.g. a C program, or a C library) that must link against a static C++ library and therefore needs the C++ runtime pulled in at link time even though its own SRCS are all .c.

Auto-detection is scoped to exactly the three C++ extensions mk.prog.mk/mk.lib.mk already recognize for compiling (cc, cpp, cxx -- new shared constant _CXX_EXTS in mk.common.mk) -- deliberately NOT reusing sys.mk's own free CXX_SUFFIXES variable (.C .cc .cpp .cxx, confirmed already populated by bmake's own sys.mk with zero .include needed) as the detection list, to avoid silently widening SRCS auto-discovery scope to a fourth extension (.C) that mk.prog.mk's/mk.lib.mk's `find src ...` auto-discovery does not search for today. Widening to .C is a separate, deferred decision, not bundled into this bug fix.
