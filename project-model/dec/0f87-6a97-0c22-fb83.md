# Implement the PARENT_WS PREREQS fallback: forward PARENT_WS through both recursion levels, search it only when the local sibling framework is absent

Three-part fix: (1) mk.workspace.mk and mk.framework.mk now forward PARENT_WS=${PARENT_WS} alongside the existing TARGET/TARGET_ARCH/TOOLCHAIN/BMK_MKDIR forwarding, at both the workspace-to-framework and framework-to-module recursion points. (2) mk.lib.mk/mk.prog.mk's PREREQS loop now checks the local sibling first (unchanged, exists(${_FWDIR}/../${_p})) and only searches PARENT_WS entries, in declared order, when that check fails -- local-vs-parent precedence falls straight out of the if/else structure, not a separate rule. (3) Two new test cases close the gap: 28-prereq-parent-link (a PREREQS framework existing ONLY in a PARENT_WS workspace resolves, links, and runs correctly) and 29-prereq-local-shadows-parent (the same framework existing in BOTH the local and a parent workspace: compiles against the LOCAL header, links against the LOCAL library, and -- verified by actually running the binary with both build outputs on the loader path simultaneously -- executes the LOCAL implementation, not the parent's, confirming this isn't just a build-time artifact of search order but genuinely correct at runtime too).
