# IMPORT= resolution is a four-step ladder, first match wins: (1) env/CLI ${LIB:tu}_PREFIX or ${LIB:tu}_CFLAGS+${LIB:tu}_LIBS, (2) mk/ hooks setting IMPORT_PREFIX or IMPORT_CFLAGS+IMPORT_LIBS, (3) pkg-config against IMPORT=pkg:<name> (or a literal IMPORT=prefix:<dir>, skipping pkg-config), (4) probing mk.paths.<os>.mk's own _TOOL_PREFIXES for lib<LIB>.* -- an unresolved import is a parse-time .error naming the module, target key, and every source tried

IMPORT= syntax: `pkg:<name>` (pkg-config), `prefix:<dir>` (direct, skips pkg-config entirely), or empty (values must come from step 1 or 2 -- no pkg-config/probing attempted). Step 3's pkg-config invocation captures --cflags, --libs (for the D2/link-transitivity mechanism, --libs --static specifically, to also capture Libs.private), --modversion, and --variable=libdir -- extra .pc search directories come from a new, empty-by-default _PKG_CONFIG_EXTRA_DIRS (mk.paths.<os>.mk's own extension point, analogous to _TOOL_PREFIXES; no real per-OS entries populated this round -- no concrete motivating path could be verified from this host, e.g. lasviewer's own PROJ9-via-GDAL case is project-specific to that acceptance target, item 8, not a generic Bmake It default). Cross-compilation: when TARGET differs from the native host OS label, PKG_CONFIG_SYSROOT_DIR/PKG_CONFIG_LIBDIR are set from the same BMK_<OS>_SYSROOT= variable mk.toolchain.llvm.mk's own cross branches already require, and PKG_CONFIG_PATH is left unset in that case specifically so host .pc files are never read -- implemented per the brief's own explicit requirement, but not empirically verified end-to-end (no foreign sysroot with real .pc files available from this host; cross-compilation itself is explicitly out of scope for this round beyond keeping this behavior correct).

Step 4 (probing) derives candidate prefixes from _TOOL_PREFIXES:H (dirname of each bin/ entry, already defined per-OS in mk.paths.<os>.mk) rather than inventing a second prefix list.
