# LIBS= link transitivity is automatic, uniformly for compiled and imported static libraries: every library module writes its own flattened direct link deps to lib<LIB>.linkdeps alongside the library file itself, and every consumer's LIBS= loop reads and appends each entry's .linkdeps content (if present) in addition to -l<name>

Mechanism: lib<LIB>.linkdeps is a small text file of extra -l/-L flags, written alongside lib<LIB>.{a,so,dylib} in the SAME build/<KEY>/lib/ directory (so it travels through the existing copy-up mechanism automatically, and is found via the existing _LIB_SEARCH_DIRS the same way the library file itself already is -- no new search-path variable). Content is flattened, not a raw pointer to "go look up LIBS= elsewhere": a compiled library's own linkdeps file already contains its OWN LIBS= expanded through EACH of THEIR OWN already-written .linkdeps files (recursive by construction -- build order already guarantees a dependency is fully built, .linkdeps included, before anything that depends on it starts). An imported library's linkdeps file is `_IMPORT_LIBS` (pkg-config's own `--libs --static` output, already the correct transitive set for that package) minus its own self `-l<LIB>`/`-L<owndir>` tokens.

Real-world consequence, matching this project's own change-scope discipline: this changes existing behavior for EVERY module's LIBS=, not just IMPORT= ones -- a compiled static library's own transitive deps now follow it automatically where they previously required every consumer to list them by hand. Explicitly in scope per the brief's own instruction ("Implement whatever is decided for own and imported libraries at the same time") and per this session's own D2 answer.

No found-guard against the rare case of the same library name resolving in more than one _LIB_SEARCH_DIRS entry (shadowing): duplicate -l/-L flags are harmless to a linker, so the mild redundancy is an accepted simplification, not a correctness gap.
