# A shared-library module declares DELAYLOAD=yes|no (default no); its module writes it beside lib<name>.linkdeps, as it does its link dependencies, and every module linking it reads it; a consumer overrides it per library with DELAYLOAD.<lib>=yes|no. Delay loading is a Windows linker feature: MSVC and lld-link /DELAYLOAD:<lib>.dll with delayimp.lib, mingw-w64 a delay-import library (dlltool --output-delaylib, llvm-dlltool -y) in place of the import library. Elsewhere it does not exist: a library's default has no effect there (documented), and a consumer's explicit DELAYLOAD.<lib>=yes on such a target is reported, not silently dropped

Not mapped: macOS weak linking (-weak_library) loads the library at start if present and only tolerates its absence -- a different promise; ELF loads every DT_NEEDED library at start (lazy binding is about symbols), the equivalent there is dlopen. Constraints: a DLL that exports data cannot be delay-loaded (MSVC LNK1194) -- a library declaring DELAYLOAD=yes must not; a failed delay load raises an SEH exception (MSVC) unless a failure hook turns it into an error. Applies to the direct link only (a library's own dependencies follow their own defaults). To verify: MSVC, mingw-w64 with GNU ld and with lld; a test where the program starts without the DLL and fails cleanly only at the first call.
