# mk.toolchain.<name>.mk must explicitly set CC/CXX/LD/AR/AS to concrete cross-compiler paths/binaries based on TARGET/TARGET_ARCH/TOOLCHAIN, following the same external-orchestration pattern every bsd-make lineage (FreeBSD Makefile.inc1, NetBSD build.sh) uses; locating each toolchain's compiler must search PATH (or a defined list of install prefixes), never rely on a single hardcoded absolute path, and must fail loudly rather than silently substituting a different compiler when the requested toolchain cannot be found

Supersedes REQ-toolchain-mk-must-set-explicit-cc-paths-req-v4 (extends it; the cross-compiler-path-mapping content is unchanged). mk.toolchain.<name>.mk needs its own explicit lookup/naming-convention logic mapping (TARGET, TARGET_ARCH, TOOLCHAIN) combinations to real compiler binary paths, and set CC/CXX/LD/AR/AS to those concrete paths directly -- mirroring how NetBSD's build.sh and FreeBSD's Makefile.inc1 do it for their own base-system builds. New in this version: locating the HOST-native compiler for a given toolchain (the non-cross-compiling case) must not rely on a single hardcoded absolute path such as exists(/usr/bin/clang) or exists(/usr/bin/gcc). It must search PATH, or a defined list of common install prefixes (/usr/bin, /usr/local/bin, /opt/local/bin for MacPorts, /usr/pkg/bin for pkgsrc, etc.), and if the requested toolchain's compiler cannot be located by any of them, the build must fail with a clear error naming what was requested and where it looked -- never silently fall through to whatever plain cc/cxx happens to resolve to, which may be an entirely different compiler.

Why this exists as a supersession rather than an edit: found empirically on real NetBSD with clang installed via pkgsrc to /usr/pkg/bin/clang (not /usr/bin/clang). With TOOLCHAIN=llvm explicitly requested and clang genuinely on PATH, the build silently used plain cc (which happened to be GCC on that system) instead -- no error, no warning. The user confirmed this is a defect to fix, not an acceptable convenience shortcut (DEC-toolchain-detection-must-search-path-dec), and that it is the same class of mistake as DEC-nested-invocation-reentrancy-guard-dec's hardcoded-path finding: a hardcoded absolute path standing in for a robust lookup.
