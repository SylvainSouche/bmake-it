# Generated headers are build artifacts, not source: private by default in module build/<KEY>/include/; explicitly-promoted public ones are copied up to a generated-only framework build/<KEY>/include/, which IS consulted (alongside fw/include/) when resolving a PREREQS frameworks headers; no workspace-level build/<KEY>/include/ is ever used for compilation

Refines REQ-headers-resolved-from-source-req and REQ-module-level-build-subdirs-req. Module level: generated headers (from lex/yacc or other tooling) land in module/build/<KEY>/include/, private to that module by default. Promotion: a module can declare specific generated headers as public (exact declaration macro TBD, open follow-up); on module build, those are copied up to framework/build/<KEY>/include/, which contains ONLY generated headers promoted this way (never hand-written ones -- those stay exclusively in fw/include/). Cross-framework header resolution (REQ-headers-resolved-from-source-req) is amended: for a PREREQS-declared framework, the search covers BOTH its fw/include/ (source) and its build/<KEY>/include/ (promoted generated) -- this is the one deliberate exception to build/<KEY>/ never being consulted for headers. Workspace level: no build/<KEY>/include/ exists for compile-time use at all; any workspace-wide header consolidation happens only during packaging/install (REQ-packaging-per-format-targets-req), never during ordinary compilation.
