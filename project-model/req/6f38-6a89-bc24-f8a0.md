# Both modules and frameworks may carry resource files (non-source runtime data); resources support per-target variants with a fallback hierarchy, and are staged into build/<KEY>/ alongside obj/bin/lib, copied upward module to framework to workspace the same way as linked artifacts

A module and/or a framework may each have their own resource-file source location (naming of that source directory -- e.g. res/, resources/ -- not yet decided, tentative working name 'res/' pending a naming pass alongside src/, include/, local/include/). Resources are staged into the target's build/<KEY>/ tree (see REQ-build-output-tree-structure) in a dedicated subdirectory alongside obj/, bin/, lib/ (tentatively 'res/' or 'share/', name TBD), and follow the same copy-upward aggregation from module level to framework level to workspace level as linked artifacts (REQ-aggregation-step-copies-outputs) -- no separate 'runtime view' materialization step. Resources support per-target variants: a resource can have a generic version plus more specific overrides, with the most specific applicable variant winning at staging time (fallback chain, analogous to real mkmk's specifics_$OS hierarchy, see OBS-mkmk-runtime-view-and-resources). Open follow-ups: (a) exact resource source-directory name(s) at module and framework level, (b) exact variant fallback levels for our compound target key -- e.g. does specificity go full-target > OS-only > generic, or some other granularity -- not yet decided.
