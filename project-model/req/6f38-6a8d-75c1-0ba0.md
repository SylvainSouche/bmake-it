# TARGET=/TARGET_ARCH= variable NAMES are still reused (for familiarity with bsd make convention), but the actual cross-compiler SELECTION logic must be implemented by this project itself (in mk.toolchain.<name>.mk or a new mk.target.mk), not inherited from bsd.prog.mk/bsd.lib.mk, which do nothing with these variables outside FreeBSDs base-system build infrastructure

Corrects REQ-target-selection-uses-bmake-native-vars-req in light of OBS-validation-target-arch-inert-without-basesystem: reusing the TARGET=/TARGET_ARCH= NAMES remains the right call for familiarity, but the claim that this reuse gets working cross-compilation 'for free' from bsd.prog.mk/bsd.lib.mk is corrected -- it does not. mk.toolchain.<name>.mk (REQ-toolchain-triggers-dedicated-mk-file-req) must itself branch on TARGET/TARGET_ARCH to select the actual cross-compiler binary/flags (e.g. a real cross-toolchain triple, or clang --target=<triple> style flags) and set CC/CXX/LD/AR/AS accordingly -- this is now understood as required custom logic, not inherited behavior. This applies to every phase-1 cross-compile scenario (e.g. building freebsd-amd64 targets from a macos-arm64 host) and is a meaningful new implementation task, not just wiring.
