# Windows target support is available via three toolchain paths -- tier 1: native MSVC (cl.exe/link.exe) run from a Cygwin-hosted bmake shell, command-line only, matching every other platform's workflow; tier 1: Cygwin-native gcc/llvm run the same way; tier 2: mingw-w64 cross-compilation from any capable host, no Cygwin required. All three produce genuine win-target output

<!-- rationale, detail, alternatives considered -->

**Architecture scoping (CON-cygwin-scoped-to-x86-family-only):** Cygwin's
own cygwin1.dll runtime has no ARM64 port -- on an ARM64 Windows host it
only ever runs as x86_64 code under Windows' built-in x64 emulation, never
natively. This applies to BOTH of Cygwin's roles here: as the host-side
supplier of sh/bmake/tooling for tier-1 MSVC builds (that shell and bmake
itself are x86_64-under-emulation, regardless of the true host CPU), and
as the "Cygwin-native gcc/llvm" tier-1 ABI in its own right (that gcc/
clang is likewise x86_64-hosted and has no built-in arm64-target
cross-compilation of its own). Neither role can ever produce or represent
`TARGET_ARCH=arm64` win-target output. When TARGET_ARCH=arm64 output is
actually wanted, the only valid paths are MSVC (tier 1 -- a genuinely
multi-arch-capable toolchain per the host Visual Studio install, able to
target x86/x64/arm64 regardless of host arch) or mingw-w64 cross-compilation
(tier 2, via an aarch64-w64-mingw32 sysroot, from any host). "Cygwin" is
never itself a target-arch axis -- it is a host-tooling / ABI-flavor
choice orthogonal to, and narrower than, TARGET_ARCH.
