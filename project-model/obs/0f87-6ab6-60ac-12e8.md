# IMPORT= staging (_stage_import:) produced broken/leaking dylib symlinks against real macOS packages (PDAL/GDAL/GLFW)

`_stage_import:`'s lib<LIB>.* staging (`import-staging-req`) globbed
`lib<LIB>.<ext>*` anchored on the search extension (`a`/`so`/`dylib`) and
copied matches verbatim via `cp -a`. On macOS the version number
precedes the extension (`libfoo.34.dylib`, `libfoo.34.3.5.dylib`) rather
than following it the way ELF does (`libfoo.so.34`) -- so the glob only
ever matched the single unversioned `libfoo.dylib` symlink. `cp -a`
preserves a symlink as a symlink rather than following it, so the copy
either went dangling (the real target's name never matched the
extension-anchored glob, so it was never staged alongside it) or, for an
absolute-target symlink (as MacPorts/Homebrew commonly produce), it
silently pointed back into the original source prefix instead of the
staged build tree.

Either way the consumer binary's runtime loader -- which looks for the
library's own embedded `install_name`, typically the SONAME-equivalent
major-version name (e.g. `@rpath/libfoo.34.dylib`), not the unversioned
name `-lfoo` resolves at link time -- fails to find it. `-lfoo` linking
itself could still succeed (the unversioned symlink, even if dangling on
disk, is enough for the linker to accept `-lfoo` at link time on some
toolchains), which is why this surfaced as a runtime failure, not a
build failure.

Found while importing real macOS packages (PDAL, GDAL, GLFW) via
`IMPORT=pkg:`/`prefix:` in a separate session, relayed back into this
one. Affects `pkg:`/`prefix:`/`fetch-bin:` staging alike (all three
route through `_stage_import:`); `IMPORT=fetch:` (source kind) is
unaffected since it compiles from source rather than staging a prebuilt
artifact.
