# Framework/workspace 'all' and 'test' always exit 0 even when a module/framework genuinely failed, with FAIL_FAST=no (the default)

Root cause identified by reading the actual recipe, not just observing the symptom: mk.framework.mk's _build_modules: and mk.workspace.mk's _build_frameworks: both unroll their .for loop into one shell command PER iteration (a new /bin/sh -c per SUBDIR_MODULES/SUBDIR_FRAMEWORKS entry, since each iteration is a separate recipe line once .for expands). Each of those per-iteration shell commands ends with `cp -a "$_rundir" .../runs/latest`, which (almost) always succeeds -- so that trailing cp's own exit status, not the module/framework build's real one a few lines earlier, is what bmake sees as that recipe line's exit code. A genuine build failure is therefore invisible to make's own line-level failure tracking, REGARDLESS of FAIL_FAST=, which only controls whether the loop keeps going after a failure it already can't see for exit-code purposes -- the intended default (continue past one module's failure) already worked correctly, only the FINAL exit code was wrong.

The same masking does NOT affect module-level `bmake test` (mk.test.mk's own test: target correctly ends with `exit $$_rc`, confirmed by reading it) or the per-iteration $$_trc capture in mk.framework.mk's/mk.workspace.mk's own test: loops (which correctly compute the real per-module/per-framework exit code into $$_trc each iteration) -- but that correctly-computed $$_trc is only ever acted on when FAIL_FAST=yes; with FAIL_FAST=no (the default) it is silently discarded once the loop moves to the next iteration, for the same one-shell-per-iteration reason.

A `build.failed` marker file already exists per module/framework run (`touch "$$_rundir/build.failed"` on failure, already written for exactly this purpose apparently but never read back by anything) -- the fix does not need new state for the build side, only for the previously-unwritten test side.
