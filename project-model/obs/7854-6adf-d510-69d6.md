# Whole-suite runs on the Windows host with ABI=mingw (58 pass/29 fail) and TOOLCHAIN=msvc from the EWDK (46/41) found, besides case-side issues: (1) MSVC: CC carries INCLUDE="F:\Program Files\...;..."; the link recipes (echo "${_CCLINK} ..."), the inputs hash (printf '%s' "CC=${CC} ...") and the FETCH_BUILD export/fingerprint pasted CC inside double quotes, so its own quotes ended the string and its ;s split the line ('F:Program: command not found'), in every module; an installed Visual Studio's 'C:\Program Files (x86)' would hit it too. (2) mingw: the mingw pkg-config wrapper prefixes its sysroot to every path, also of a .pc file outside the sysroot (given through PKG_CONFIG_PATH), even reporting a pcfiledir that does not exist. (3) ABI=mingw with TARGET=linux gave the key linux-amd64-mingw instead of an error. (4) A hook re-pointing _TOOL_PREFIXES reached no mingw probing. (5) bmake run put the mingw runtime bin/ before the workspace bin/, against its own requirement. (6) MSVC: a DLL with no __declspec(dllexport) gets no import library, so ~15 cases' plain C libraries cannot be linked -- msvc-shared-lib-export-req's mechanism is still undecided. Case side: Windows-runtime programs print \r\n and see PATH in Windows form; fake libraries were built with Cygwin's cc; the C++ runtime DLLs were not on PATH; a spy pkg-config had the host's name.
