# The compiler-native -MD dependency-tracking wiring confirmed working is specific to FreeBSD's own actual bsd.sys.mk -- NOT a general BSD-make-family property. Cross-checked against NetBSD's own bundled mk-netbsd set: zero -MD flags, zero per-object dependency files, and touching a header correctly produced NO rebuild at all. Whether MacPorts' own bsdmake port (a phase-1 target host) includes this wiring is unknown and untestable in this sandbox

Directly cross-checked OBS-validation-compiler-native-md-dependency-tracking-confirmed against a second bsd-make lineage to test whether that finding generalizes. Built and ran the identical PROG=hello test (main.c + greet.c including greet.h) using NetBSD's own bundled mk-netbsd set (shipped inside the bmake Debian package, self-consistent with its own make binary -- the genuinely portable lineage, as opposed to FreeBSDs own base-system-specific share/mk fetched from GitHub). Result: the compile commands were plain `cc -O2 -Wno-error -Werror -c main.c` with no -MD flag whatsoever; no .depend.* files were produced; and touching greet.h and rebuilding triggered NO recompilation at all -- confirming zero dependency tracking is wired in by default in this lineage. grep across every .mk file in mk-netbsd found zero references to -MD. This means REQ-compiler-native-dependency-tracking-req's confirmed-working claim is CORRECT but was stated too broadly -- it holds specifically for FreeBSDs own actual bsd.sys.mk (i.e. on a real FreeBSD host using its native /usr/share/mk), not as a general property inherited from using any bsd-make-family .include. Since this projects phase-1 hosts are macOS (via MacPorts bsdmake) and FreeBSD -- not NetBSD -- the practically relevant open question is whether MacPorts own bsdmake port includes equivalent -MD wiring in its own bsd.sys.mk, which is unknown and cannot be tested in this sandbox (no macOS/MacPorts environment available, consistent with the standing Tier 1.3 gap in the validation plan).
