# mk.prog.mk/mk.lib.mk never track per-source header dependencies at all -- changing a header does not trigger a rebuild, and the model's own 'confirmed' REQ claiming otherwise doesn't apply to this project's architecture

Root cause: REQ-compiler-native-dependency-tracking-req (0f87-6a91-4c89-ba40, status confirmed) claims bsd.sys.mk wires -MD/-MF into every compile "with no custom wiring needed" -- true of real bsd.sys.mk's own canned .c.o suffix-transformation rule, but Bmake It's mk.prog.mk/mk.lib.mk never reach that mechanism at all: they define fully explicit ${_OBJDIR}/${_s:R}.o: ${.CURDIR}/src/${_s} target:source rules with hand-written recipes, and (confirmed by grepping every .include in mk.common.mk/mk.prog.mk/mk.lib.mk/mk.framework.mk/mk.workspace.mk) never .include bsd.sys.mk, bsd.prog.mk, bsd.lib.mk, or any other real bsd.*.mk file -- only Bmake It's own mk.*.mk role files. So the confirmed REQ describes a mechanism this project's own compile rules never touch, on any host, not just the ones the refining REQ (md-dependency-tracking-freebsd-specific-req) already flagged as unconfirmed (NetBSD: confirmed absent; MacPorts/macOS: previously untestable without a real Mac -- now tested, on this exact host, and the result is that the question was moot regardless: Bmake It's own explicit recipes bypass the mechanism entirely, independent of what any host's bsd.sys.mk itself contains).

README.md's own "Known limitations" (".depend / mkdep-style header dependency tracking not yet wired") was the accurate statement all along; the confirmed REQ was the stale one.
