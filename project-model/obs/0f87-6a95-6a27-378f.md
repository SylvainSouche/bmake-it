# Module discovery and dependency-order analysis mechanisms (gen-mod-order.sh, gen-fw-order.sh) shell out to nested bmake invocations with no reentrancy guard and no absolute-path resolution of the make binary, causing redundant re-discovery on every nested parse and a catastrophic self-recursion when the invoked name resolves back to a wrapper of itself

Testing the impl/rade-bmake implementation on real Linux (not just macOS) surfaced a genuine self-reentrant-invocation bug: the test harness's bmake wrapper, when $BMAKE was a bare command name rather than an absolute path, called itself recursively without bound (each call prepending more -m flags), because the wrapper is installed on PATH under the name 'bmake' and its own body invokes 'bmake' unqualified.

Tracing the mechanism that triggered it (gen-mod-order.sh's _bmake_q(), called from mk.framework.mk's module-discovery/ordering step) showed the risk is not confined to the test harness. In the real tool: mk.workspace.mk's framework discovery (gen-fw-order.sh) queries each framework's PREREQS via a nested 'bmake -f Fw/makefile -V PREREQS'. Because that parse evaluates the framework's full makefile, it ALSO unconditionally re-triggers mk.framework.mk's own module-discovery step (gen-mod-order.sh), which itself shells out to bmake once per module. The same module-discovery step runs again when the workspace's actual build recursion ('${MAKE} -C ${_f} all') reaches that framework, since the discovery script deletes and regenerates its cache file unconditionally on every parse, with no guard against concurrent or nested re-entry.

In normal (non-test-harness) use this terminates -- it is not an infinite loop -- but it is redundant work proportional to frameworks x modules on every build, and the unconditional 'rm -f <cache> then regenerate' pattern with no lock is a real race if the same directory's discovery is ever triggered concurrently (e.g. under a future parallel build). The catastrophic self-recursion found on Linux is the extreme case of this same underlying pattern: a mechanism that shells out to a nested make invocation for discovery or dependency-order analysis, with no guard against the invocation re-entering itself or racing another in-flight instance of itself.
