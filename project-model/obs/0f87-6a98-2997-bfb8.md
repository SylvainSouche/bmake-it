# The NetBSD arm64 VM's flaky/inconsistent SSH behavior all session was real filesystem corruption from repeated unclean QEMU kills, not a networking or auth quirk

This session killed this VM's qemu-system-aarch64 process directly (plain 'kill', no guest-side graceful shutdown) many times while debugging headless. On the next boot the root filesystem failed its automatic fsck with real corruption (INCORRECT BLOCK COUNT, DUP block references), which aborted the boot into single-user recovery -- exactly explaining the inconsistent "timed out during banner exchange" vs "connection reset by peer" behavior seen across many earlier attempts (the filesystem state, and therefore how far boot got before something touched a corrupted area, differed run to run). After a manual 'fsck_ffs -y /' repair and 'exit' to resume boot, the system came up multi-user but sshd itself failed separately ("no hostkeys available") because /etc/ssh's host keys were apparently among what the corruption/repair lost. Regenerating them with 'ssh-keygen -A' and starting sshd manually fixed that. Root cause of the corruption: no graceful shutdown path existed anywhere in this session's VM tooling -- every kill was a hard stop equivalent to pulling power. This is a process/tooling gap, not a NetBSD or QEMU defect.
