# Open topic, not yet scoped: a fourth architectural level above workspace (Collection -> Workspace(=Application) -> Framework -> Module), functioning like a ports collection (FreeBSD Ports / NetBSD pkgsrc) -- holds multiple independent applications, each its own workspace, auto-discovered the same way a workspace discovers frameworks (dirs whose makefile declares PARENT_WS=)

Does NOT aggregate output the way workspace aggregates frameworks into build/<KEY>/ -- that's a real difference from the existing WS->FW relationship, not just one more level of the same pattern. Can be ASKED to aggregate on demand for a specific purpose, e.g. producing a software layer for a target system -- ties directly to vm-image-caching-layering-unaddressed's OS/software/data layer discussion. Complementary to, not replacing, PARENT_WS= (which stays a dependency/reuse relationship between any two workspaces, collection or not). The parked external-tool-generation-config-topic may be directly relevant here too -- a collection pulling in external modules/packages is a natural use of that same mechanism.
