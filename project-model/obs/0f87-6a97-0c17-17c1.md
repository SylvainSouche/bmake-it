# PREREQS resolution never actually searched PARENT_WS, despite a confirmed REQ requiring it

REQ-headers-resolved-from-source-req explicitly requires a PREREQS framework to be resolved first in the current workspace, then falling back through PARENT_WS workspaces in declared order. mk.lib.mk and mk.prog.mk's PREREQS loop only ever checked ${_FWDIR}/../${_p} (a same-workspace sibling) -- no PARENT_WS fallback existed at all. Compounding this, PARENT_WS itself was never forwarded through the recursive build chain: mk.workspace.mk's framework recursion and mk.framework.mk's module recursion both forwarded TARGET/TARGET_ARCH/TOOLCHAIN/BMK_MKDIR but not PARENT_WS, so even a fixed lookup would have seen it as always-empty at the module level where the lookup actually happens. Existing test case 18-parent-ws only checked that the PARENT_WS macro itself resolves to an absolute string -- its own comment already flagged "Full cross-workspace header search may still be TODO in implementation" -- but no test ever exercised an actual cross-workspace build+link+run, so this sat unnoticed.
