# Alpine/musl cannot resolve a custom shared library's exported symbol at runtime, even in a minimal, product-independent reproduction

A freshly-built, correctly-exported shared library (confirmed via readelf --dyn-syms: symbol present, GLOBAL, DEFAULT visibility, correct SONAME, correct DT_NEEDED on the consumer) fails at load time with 'Error relocating <bin>: <symbol>: symbol not found' on Alpine/musl. Isolated via a minimal 2-file repro (one .c exporting one function, one .c calling it via a shared lib) with NO project code involved -- ruling out rade-bmake entirely. Systematically eliminated: not gcc-specific (clang fails identically); not an Alpine version regression (reproduces on both alpine:3.19, gcc 13.2.1, and alpine:latest, gcc 15.2.0); not a --hash-style issue (sysv/gnu/both all fail identically); not a qemu-user emulation artifact (reproduces natively on arm64 Alpine with no --platform emulation involved); not stale overlay2/mmap caching (reproduces with fresh filenames in a fresh container). A control test confirms the function itself is correct (statically linking the same .o works and prints the expected output). Root cause not identified beyond this; not investigated further given musl's 2nd-tier/best-effort status in the platform matrix. This was previously masked in the existing test suite: case 10-prog-link-lib hits the identical failure but has a soft '|| echo run skipped' fallback that always reports PASS regardless -- the new tests are strict specifically because proving PARENT_WS runtime correctness (not just build-time) was the point of adding them.
