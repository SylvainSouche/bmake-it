# The macOS tart VM was never actually stuck -- an expect script bug (case-sensitive 'password:' match vs the real 'Password:' prompt) made every provisioning attempt hang indefinitely, looking exactly like an unreachable/hung VM

Two separate hour-plus 'stuck VM' episodes (0.0% CPU, no route to host) were actually the VM booting/idling normally while provision-macos-vm.sh's ssh_pw() helper waited forever inside its own expect loop for a pattern that could never match: the script matched literal "password:" but this VM's actual prompt is "Password:" (capital P), and expect's string matching is case-sensitive by default. Found by connecting manually with a bare `ssh` command outside the script and seeing the real prompt text directly. Fixed with -nocase in the expect pattern. Once fixed, the full bootstrap (MacPorts install, bmake + gcc14 + llvm-22 via port, SSH key installation) completed in a few minutes with no further issues, and the full 27+2-case suite passed 29/29 under llvm and the expected 27/29 (2 known toolchain-default-assertion cases) under gcc -- confirming a genuine, non-substituted MacPorts gcc was used (case 13's own output showed "gcc OS_ARCH=macos-arm64-gcc"), which itself required a second, separate fix: non-interactive ssh sessions get PATH=/usr/bin:/bin:/usr/sbin:/sbin (no /opt/local/bin), so mk.toolchain.gcc.mk's 'command -v gcc' would otherwise have silently resolved to Apple clang's /usr/bin/gcc wrapper instead of the real compiler -- run-native-macos.sh now exports PATH explicitly before invoking the suite.
