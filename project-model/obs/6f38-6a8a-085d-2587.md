# Cygwin-native gcc and a mingw-w64 cross-compiler are separate packages/toolchains; which one produces a cygwin1.dll dependency is determined by the target triple, not by the shell/OS hosting the compiler process

User asked whether cross-compiling using a toolchain installed under Cygwin inevitably drags in Cygwin runtime dependencies. Clarified: no -- Cygwin's native gcc (target x86_64-pc-cygwin, links cygwin1.dll) and a mingw-w64 cross-compiler package (target x86_64-w64-mingw32, links MinGW's own runtime) are two entirely separate toolchains that both happen to be installable via Cygwin's package manager. The output binary's runtime dependency is determined by the target triple the specific compiler package was built for, not by which shell/OS process is invoking it -- running a mingw-w64 cross-compiler from inside a Cygwin bash shell produces the same dependency-free native Windows binary as running that same compiler from Linux/WSL/macOS. The actual risk is accidentally selecting the wrong package (Cygwin-native vs mingw-w64-cross), not an inherent limitation of building from within Cygwin. This refines/clarifies REQ-win-target-via-cross-toolchain-req's deferred mingw-vs-Cygwin distinction with the correct technical mental model, without changing its confirmed scope or deferral status.
