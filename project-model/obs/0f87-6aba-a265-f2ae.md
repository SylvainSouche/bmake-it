# Continued lasviewer migration (GLFW/GDAL/PDAL/Dear ImGui) surfaced five more real bugs: (1) a program isn't relinked when a static library it uses from ANOTHER framework changes -- most serious, silently tests a stale binary; (2-5) FETCH_BUILD=cmake forwards the module's own consumer-side LDFLAGS (breaking cmake's own compiler check), the <LIB>_BUILDING macro (invalid when LIB contains '-'), no dependency install-prefix forwarding (a fetch-built dependency can't find a sibling fetch-built dependency), and no macOS deployment-target forwarding (linker warnings); (6) fetch:'s own re-extraction still races a hook that pre-creates an object subdirectory before _fetch_import's rm -rf/mkdir -p only recreates the TOP-LEVEL object dir

User's own words, verbatim (pasted as "bmake-it problems this migration hit"):

> * A program isn't relinked when a static library it uses from another
>   framework changes. This is the most serious one: it had me testing
>   a stale binary for a while. Until it's fixed, delete `lasviewer`'s
>   binary (or run `bmake clean`) after changing `Geo`.
> * `FETCH_BUILD` passes the wrong things to CMake:
>    * the module's own link flags break CMake's first compiler check;
>    * a macro derived from the library name is invalid when the name
>      contains `-`;
>    * a dependency's install prefix isn't passed, so copc-lib couldn't
>      find laz-perf without help;
>    * the macOS deployment target isn't passed, which causes linker
>      warnings.
> * ImGui's `fetch:` workaround had to change: on a first build,
>   extracting the archive clears the object directory after the hook
>   had already created the subdirectory.

Root causes confirmed by reading the code (not assumed):

1. **Stale relink**: `${_BINOUT}: ${OBJS}` (mk.prog.mk) and
   `${_LIBOUT_DIR}/${SHLIB_NAME}: ${OBJS}` (mk.lib.mk) list only this
   module's OWN objects as real make prerequisites -- the `LIBS=`
   existence-check loop inside each recipe is a shell presence test,
   not a make dependency, so a library rebuilt elsewhere never appears
   in the prerequisite graph and bmake has no reason to relink.
2. **CMake's own compiler check broken**: `_fetch_build:` forwards the
   module's fully-assembled `LDFLAGS` (which accumulates THIS module's
   own consumer-side `-L`/`-l`/`-Wl,-rpath,` flags for linking against
   sibling frameworks/prereqs) into CMake's environment; CMake's own
   "Check for working C compiler" step does a trial compile+link using
   that same environment, and an unrelated/stale `-l<name>` or rpath
   entry can make that trial link fail.
3. **Invalid macro name**: `mk.common.mk`'s `CFLAGS += -D${LIB:tu}_BUILDING`
   applies unconditionally to every lib module, including a
   `FETCH_BUILD=` one whose `CFLAGS` also gets forwarded into the
   upstream build -- `${LIB:tu}` is not sanitized, so `LIB=laz-perf`
   produces `-DLAZ-PERF_BUILDING`, not a valid preprocessor macro name
   (and not a valid single compiler argument either).
4. **No cross-fetch-dependency prefix propagation**: each `FETCH_BUILD=`
   module installs into its own, private `work/_install/` prefix
   (`_FETCH_INSTALL_PREFIX`) with nothing exposing that path to a
   SIBLING fetch-built module's own `FETCH_BUILD=cmake` invocation, so
   `find_package()`/equivalent inside a dependent's own CMake configure
   can't find it.
5. **No deployment-target forwarding**: `_fetch_build:` forwards
   `CC`/`CXX`/`CFLAGS`/`CXXFLAGS`/`LDFLAGS` but not
   `MACOSX_DEPLOYMENT_TARGET`/`-mmacosx-version-min=`, so a fetched
   library built via CMake/Meson can target a different minimum macOS
   version than the rest of the build, producing linker warnings.
6. **Object-dir race, second form**: `_fetch_import:`'s genuine-
   re-extraction path does `rm -rf ${_OBJDIR}; mkdir -p ${_OBJDIR}`
   (added to fix an earlier, related race -- `import-staging-req`'s own
   `_fetch_import:` implementation) but only recreates the TOP-LEVEL
   `${_OBJDIR}`, not any nested subdirectory a multi-directory fetched
   source (ImGui, with backend sources under `backends/`) needs before
   its own per-source-file compile rule can write there.
