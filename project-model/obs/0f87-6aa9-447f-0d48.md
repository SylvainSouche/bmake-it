# Shared libraries built by mk.lib.mk were not runtime-loadable by anything outside their own build directory -- bare install_name (macOS) with no consumer-side rpath anywhere

Surfaced by the first real attempt to EXECUTE a freshly-linked binary against a freshly-built shared lib (the greet_test atf-c++ binary linking -lgreet): dyld failed with 'Library not loaded: libgreet.1.dylib' even though link-time -L/-l succeeded, because the dylib's install_name was a bare filename ('libgreet.1.dylib', not @rpath/... or an absolute path) and no consumer ever passed -rpath. Latent since implementation on 2026-09-02 -- nothing before this session had actually RUN a binary linked against a locally-built shared lib; only compile+link success had been checked. Same gap existed in mk.prog.mk for real executables, not just the test harness.
