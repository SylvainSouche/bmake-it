# gen-mod-order.sh's _bmake_q queries a module's LIB=/LIBS=/PROG= via 'bmake -f <moduledir>/makefile -V <var>' from the FRAMEWORK's own cwd -- .CURDIR inside that query is the framework directory, not the module's, silently wrong for anything .CURDIR-sensitive (module-local mk/ hook lookup) and fatal for anything that can .error during a full-file parse (an unresolvable IMPORT=)

Root cause: bmake's .CURDIR is the process's actual working directory, not wherever -f's argument happens to point -- `-f libgreet3.m/makefile` run from Fw/ leaves .CURDIR=Fw, not Fw/libgreet3.m, for the ENTIRE parse of that file. Harmless for every module role file until now, because LIB=/LIBS=/PROG= are plain literal assignments at the top of a module makefile, unaffected by .CURDIR being wrong -- nothing about them depends on it. IMPORT= support changes that: mk.lib.mk's own IMPORT= resolution block (i) computes _LOCAL_MK_DIRS from ${.CURDIR}/mk for the module's own hook lookup, silently missing a real hook file when .CURDIR points at the wrong directory, and (ii) can genuinely .error when nothing resolves -- and a .error anywhere during a -V query's full-file parse aborts the WHOLE query, poisoning even the unrelated LIB=/LIBS=/PROG= values gen-mod-order.sh actually wanted, which is how a genuinely broken import silently produced a garbage "id" (the error text itself) for that module in the topological sort's own bookkeeping, breaking ordering for every other module in the same framework too, not just the broken one.
