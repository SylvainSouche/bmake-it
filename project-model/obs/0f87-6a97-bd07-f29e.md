# FreeBSD and NetBSD amd64 both stall deterministically at the identical boot-loader-to-kernel transition point under QEMU/TCG on this host

Both official images (FreeBSD 14.3-RELEASE VM-IMAGE, NetBSD 10.1 amd64-live) hang at the exact same conceptual point -- immediately after the boot loader finishes loading kernel modules/entropy, right before jumping into the kernel proper -- with serial output frozen at an identical byte count indefinitely. Systematically ruled out via 6 independent variants, all producing the identical stall: virtio disk vs IDE disk, bare virtio-rng-pci vs an explicit -object rng-random backend, -M pc vs -M q35 chipset, smp=2 vs smp=1, and confirmed it is not waiting on stdin (sent a newline into the console, no change). Both images are hardware-accelerated fine on their native arch (this same host boots NetBSD-arm64 via hvf without issue) -- this is specific to amd64-target + accel=tcg (pure software emulation, since this host is Apple Silicon and has no hardware acceleration for a non-native target arch). Points to a QEMU 11.1.0 TCG x86_64 emulation issue on this specific host/version combination, not a rade-bmake or test-harness defect -- matches the earlier session pattern of a real, deeply-investigated external limitation (see also OBS-alpine-musl-shared-lib-runtime-symbol-resolution-broken) rather than a guessable configuration mistake.
