\begin{abstract}
\noindent
This document describes \texttt{Bmake It}, a BSD-make-based build
system for C, C++, and lex/yacc grammar sources, designed to mimic the
conceptual model of Dassault Systèmes' RADE/\texttt{mkmk} tool
(workspaces, frameworks, modules, prerequisites) while reusing real BSD
make infrastructure wherever it fits\reqfoot{CON-use-bsdmake}. Every
substantive claim in this document is footnoted with the requirement,
decision, or constraint alias from the project's discovery-driven
design record (\texttt{project-model/}) that established it, so any
statement here can be traced back to its origin and rationale.

This is a \emph{draft} document, written while the design is still
being finalized; sections marked \textbf{[open]} describe areas where
the underlying design is intentionally still undecided or deferred.
\end{abstract}

\chapter{Overview}

\section{What Bmake It Is}

\texttt{Bmake It} is a cross-platform build system for C and C++
(plus lex/yacc grammar sources, which compile down to C/C++)\reqfoot{REQ-supported-languages},
built on top of real BSD make rather than GNU make or a bespoke build
tool. Its object model — \emph{workspaces} containing \emph{frameworks}
containing \emph{modules} — is deliberately modeled on Dassault
Systèmes' RADE/\texttt{mkmk} tool, a CAA (Component Application
Architecture) build system used internally at Dassault Systèmes since
the late 1990s. Where \texttt{mkmk}'s specific mechanisms don't fit
BSD make's own idioms well, \texttt{Bmake It} diverges deliberately
rather than reproducing them exactly\reqfoot{CON-use-bsdmake}.

Three mechanisms present in real \texttt{mkmk} are explicitly
\emph{not} carried over, by design rather than oversight:

\begin{itemize}
\item No dedicated ``identity card'' special file for declaring
  prerequisites — prerequisites are declared directly in the ordinary
  framework \verb|makefile|\reqfoot{NREQ-no-identitycard-special-file}.
\item No four-level RADE header hierarchy (Public / Protected /
  Private / Local) — \texttt{Bmake It} uses a simpler three-level
  scheme instead, described in Chapter~\ref{ch:basic-usage}\reqfoot{NREQ-no-four-level-header-visibility}.
\item No \texttt{mkGetPreq}/\texttt{mkCopyPreq}-style commands for
  managing prerequisite search paths — prerequisite resolution is
  purely dynamic, with no static-copy mode and no dedicated setup
  command\reqfoot{NREQ-no-copy-preq-commands}.
\end{itemize}

\section{Design Philosophy}

The guiding principle throughout is: \emph{reuse real BSD make
variables and mechanisms wherever they already exist; introduce new,
project-specific ones only where BSD make genuinely has no
equivalent.} This shows up consistently:

\begin{itemize}
\item Target selection reuses BSD make's own \verb|TARGET=|/\verb|TARGET_ARCH=|
  convention rather than inventing new names\reqfoot{REQ-target-arch-toolchain-selection-is-custom-req}.
\item Installation reuses \verb|DESTDIR| unchanged; \verb|PREFIX|, it
  turns out, is not actually a native BSD make concept at all (see
  Section~\ref{sec:validation})\reqfoot{REQ-prefix-is-new-not-reused-req}.
\item Compile and link flags (\verb|CFLAGS|, \verb|CXXFLAGS|,
  \verb|LDFLAGS|, \verb|YFLAGS|, \verb|LFLAGS|) are the ordinary BSD
  make variables, extended via \verb|+=| — no wrapper macros the way
  real \texttt{mkmk} used \verb|LOCAL_CFLAGS|-style
  names\reqfoot{REQ-flags-reuse-bsd-native-vars-req}.
\item Debug-vs-release is controlled via BSD make's own
  \verb|DEBUG_FLAGS|, not a new \verb!MODE=debug|release! abstraction\reqfoot{REQ-debug-release-via-native-bsd-flags-req}.
\item Shared-library versioning reuses \verb|SHLIB_MAJOR|/\verb|SHLIB_MINOR|
  directly from real \verb|bsd.lib.mk|\reqfoot{REQ-shlib-major-minor-cross-platform-emission-req}.
\item The final link driver is chosen the same way real
  \verb|bsd.init.mk| chooses its internal \verb|_CCLINK| — \verb|${CXX}|
  when the module has a C++ source, \verb|${CC}| otherwise — reimplemented
  as Bmake It's own \verb|_CCLINK|, since \verb|mk.prog.mk|/\verb|mk.lib.mk|
  never \verb|.include| any real \verb|bsd.*.mk| file to inherit it
  from\reqfoot{REQ-cxx-link-driver-selection-req}.
\end{itemize}

New, project-specific concepts (\verb|PARENT_WS|, \verb|PREREQS|,
\verb|PROG|, \verb|LIB|, \verb|LIBS|, \verb|LIB_SHARED|, \verb|INCL|,
\verb|TOOLCHAIN|, \verb|LINK_CXX|) exist only for domain concepts BSD
make has no native equivalent for at all — workspace parenting,
framework prerequisites, module identity, linking, header promotion,
toolchain bundle selection, and the one link-driver case
\verb|SRCS|-based auto-detection cannot see (a C-only module linking a
static C++ library)\reqfoot{REQ-uniform-makefile-filename-req}.

\textbf{This reuse-first philosophy has real, tested limits.} An
empirical validation pass against real FreeBSD \verb|share/mk| and a
portable \texttt{bmake} binary found that several assumed
``native reuse'' cases were actually wrong: \verb|LIB_SHARED| has no
native BSD-make equivalent at all (real \verb|bsd.lib.mk| builds a
static archive whenever \verb|LIB| is set, and \emph{additionally}
builds a shared library only if \verb|SHLIB_MAJOR| is
present)\reqfoot{REQ-lib-shared-is-new-not-reused-req}, \verb|PREFIX|
does not exist in \verb|bsd.prog.mk|/\verb|bsd.lib.mk| at
all\reqfoot{REQ-prefix-is-new-not-reused-req}, and
\verb|TARGET|/\verb|TARGET_ARCH| have no effect whatsoever without
FreeBSD's full base-system build machinery, which a standalone project
does not have\reqfoot{REQ-target-arch-toolchain-selection-is-custom-req}.
These corrections are described in Section~\ref{sec:validation} and
are already reflected in the macro reference in
Chapter~\ref{ch:advanced}.

\section{The Domain Model}
\label{sec:domain-model}

\begin{description}
\item[Workspace] A set of frameworks\reqfoot{REQ-workspace-is-set-of-frameworks}.
  A workspace may declare an ordered list of \emph{parent} workspaces;
  the build searches them, in declared order, for anything not found
  locally\reqfoot{REQ-workspace-parent-search-order}. This search is
  purely dynamic — there is no physical-copy mode and no separate
  setup command, unlike real \texttt{mkmk}'s
  \texttt{mkGetPreq}/\texttt{mkCopyPreq}\reqfoot{DEC-prereq-access-dynamic-only}.
  A workspace carries no resource files of its
  own\reqfoot{NREQ-no-workspace-level-share-source}.

\item[Framework] Contains one or more modules, exposes public headers,
  and declares its prerequisite frameworks\reqfoot{REQ-framework-contains-modules}.
  A framework's prerequisite declaration is \emph{mandatory}, even when
  empty — its presence is what makes a directory auto-discoverable as
  a framework in the first place\reqfoot{REQ-prereqs-mandatory-even-empty-req}.

\item[Module] The basic link unit: a module produces exactly one
  executable, static library, or shared
  library\reqfoot{REQ-module-is-basic-link-unit}. A module's directory
  is named \verb|NAME.m|\reqfoot{REQ-module-dir-naming-convention}, and
  modules are auto-discovered by scanning — no explicit list is
  maintained by hand\reqfoot{REQ-modules-and-frameworks-auto-discovered-req}.

\item[Resource files] Non-source runtime data (icons, configuration
  files, and similar), carried by both modules and
  frameworks\reqfoot{REQ-resource-file-model}, staged through a
  three-layer \verb|share/| overlay described in
  Section~\ref{sec:resources}.
\end{description}

\section{Platform and Language Scope}
\label{sec:platform-scope}

\textbf{Languages}: C, C++, and lex/yacc grammar sources. Java,
Fortran, IDL, and Express — all supported by real \texttt{mkmk} — are
explicitly out of scope for now\reqfoot{REQ-supported-languages}.

\textbf{Hosts}: macOS (via MacPorts), Linux, and the \texttt{*BSD}
family\reqfoot{CON-cross-platform-targets}, plus Cygwin and WSL treated
as \texttt{*NIX}-like build hosts (WSL is, for build purposes, simply
Linux; no native MSVC toolchain is required)\reqfoot{REQ-windows-hosts-cygwin-wsl}.

\textbf{Phase 1} — the concrete, currently-targeted scope — is exactly
four build targets\reqfoot{REQ-phase1-concrete-targets}:
\begin{center}
\begin{tabular}{ll}
\toprule
Target key & Meaning \\
\midrule
\verb|macos-arm64| & macOS, Apple Silicon, LLVM (default toolchain) \\
\verb|macos-arm64-gcc| & macOS, Apple Silicon, GCC \\
\verb|freebsd-amd64| & FreeBSD, x86-64, LLVM (default toolchain) \\
\verb|freebsd-amd64-gcc| & FreeBSD, x86-64, GCC \\
\bottomrule
\end{tabular}
\end{center}

Everything outside this set — OpenBSD/NetBSD, per-distribution Linux
labeling, kernel-level or Darwin/XNU development, macOS \texttt{.app}
bundle output, the exact \texttt{win} ABI story (MinGW vs.\ Cygwin vs.\
MSVC), musl libc — is deliberately deferred, not designed against yet\reqfoot{REQ-userland-only-scope}.

%===============================================================
\chapter{Setting Up}
\label{ch:requirements}
\label{ch:setup}
%===============================================================

This chapter gets a host ready: a BSD make, a toolchain, the optional
tools for testing and documentation, and one line of shell
configuration. At the end, Section~\ref{sec:setup-verify} checks the
result by building the bundled example and running the project's own
test suite. For which hosts and languages are in scope at all, see
Section~\ref{sec:platform-scope}.

\section{What Every Host Needs}

\begin{description}[style=nextline]
\item[A BSD make.] \texttt{Bmake It} is a set of \verb|mk.*.mk| files for
  BSD make (\texttt{bmake}); it does not run under GNU
  make\reqfoot{CON-use-bsdmake}. On FreeBSD and NetBSD the base system's
  \texttt{make} \emph{is} bmake.
\item[A C/C++ toolchain.] LLVM (\texttt{clang}, \texttt{lld}) is the
  default, \verb|TOOLCHAIN=gcc| selects GCC, and on Windows
  \verb|TOOLCHAIN=msvc| selects Microsoft's compiler. The compiler is
  looked up in the platform's package-manager prefixes (MacPorts,
  Homebrew, pkgsrc, \verb|/usr/local|), not only on
  \verb|PATH|\reqfoot{REQ-toolchain-mk-must-set-explicit-cc-paths-req-v5}.
\item[pkg-config] for libraries imported from the system
  (\verb|IMPORT=pkg:|, Section~\ref{sec:openrider-imports}).
\item[Optional:] \texttt{flex}/\texttt{bison} (or \texttt{lex}/\texttt{yacc})
  for grammar sources; \texttt{curl} or the system's own downloader,
  \texttt{tar}, \texttt{unzip} and \texttt{patch} for fetched sources;
  \texttt{doxygen} for \verb|bmake docs|; ATF (\texttt{atf-c},
  \texttt{atf-c++}, \texttt{atf-sh}) and Kyua for \verb|bmake test|. A
  missing tool is reported by name when a module needs it, never
  assumed.
\end{description}

\section{Per Host}

\subsection*{FreeBSD}
The base system has \texttt{make} (bmake; FreeBSD 15 also installs it as
\texttt{bmake}), \texttt{clang}, \texttt{kyua}, \texttt{yacc}/\texttt{lex},
\texttt{fetch}, \texttt{unzip} and \texttt{patch}. Add the rest from
packages:
\begin{lstlisting}[language=bash]
# pkg install pkgconf gcc cmake-core doxygen atf bash
\end{lstlisting}

\subsection*{NetBSD}
The base system has \texttt{make} (bmake, under that name only),
\texttt{gcc} and ATF. Add LLVM and the tools from pkgsrc binaries:
\begin{lstlisting}[language=bash]
# pkg_add pkgconf cmake doxygen kyua clang lld
\end{lstlisting}

\subsection*{Debian, Ubuntu and other Linux}
\begin{lstlisting}[language=bash]
$ sudo apt install bmake clang lld gcc g++ pkgconf curl \
      bison flex doxygen kyua atf-sh libatf-dev unzip patch
\end{lstlisting}
The bmake of Debian/Ubuntu is older than the BSDs' (it lacks the
\verb|:mtime| modifier); \texttt{Bmake It} does not rely on anything it
lacks.

\subsection*{macOS}
Use one package manager for bmake \emph{and} the toolchain --- MacPorts,
Homebrew or pkgsrc --- not Apple's Command Line Tools, which are only a
last-resort fallback. With MacPorts, as OpenRider's continuous
integration does:
\begin{lstlisting}[language=bash]
$ sudo port -N install bmake clang-22 atf kyua pkgconfig
$ sudo port select --set clang mp-clang-22
\end{lstlisting}

\subsection*{Windows}
\texttt{Bmake It} runs in a Cygwin shell. In Cygwin's own
\verb|setup-x86_64.exe| select \texttt{bmake}, \texttt{clang},
\texttt{gcc-g++}, \texttt{pkgconf}, \texttt{curl}, \texttt{unzip} and
\texttt{patch}. Three kinds of output are then available
(Chapter~\ref{ch:cross}):
\begin{itemize}
\item Cygwin programs (the default): nothing more to install.
\item Native Windows programs with mingw-w64 (\verb|ABI=mingw|): add
  \texttt{mingw64-x86\_64-gcc-core} and \texttt{mingw64-x86\_64-gcc-g++}.
\item Native Windows programs with MSVC (\verb|TOOLCHAIN=msvc|): either
  an installed Visual Studio or Build Tools (found with
  \texttt{vswhere.exe}), or a mounted Enterprise WDK ISO given as
  \verb|BMK_EWDK_ROOT=F:\| --- no installation needed, its compiler and
  Windows SDK are used in place.
\end{itemize}
Cygwin packages neither ATF nor Kyua. Install Cygwin's \texttt{lua} and
\texttt{liblua-devel} at 5.4.4 (their \emph{test} versions --- the
stable 5.3 is too old for Lutok 0.6), \texttt{libsqlite3-devel} and
\texttt{sqlite3}, then build them into \verb|/usr/local| from their
checksummed release tarballs:
\begin{lstlisting}[language=bash]
$ sh tests/harness/provision/build-atf-kyua.sh
\end{lstlisting}
\texttt{Bmake It} finds ATF next to the Kyua it
runs\reqfoot{REQ-atf-from-kyua-prefix-req}.

\section{Pointing Your Make at Bmake It}
\label{sec:install-env}

Every role file (\verb|mk.workspace.mk|, \verb|mk.prog.mk|, \ldots) is
found through bmake's own search path for shared make files,
\verb|MAKESYSPATH|. Set it once:
\begin{lstlisting}[language=bash]
$ sh /path/to/bmake-it/scripts/install-env.sh
\end{lstlisting}
The script adds a marked block to your shell's start-up file
(\verb|~/.profile|, \verb|~/.bashrc|, \verb|~/.zshrc| or fish's
\verb|config.fish|), shows the change and asks first (\verb|-y| skips
the question, \verb|--uninstall| removes the block). It uses
\texttt{bmake}, or a \texttt{make} that is bmake, as on
NetBSD\reqfoot{REQ-install-env-script-req}. The resulting line, which you
may also write by hand, looks like:
\begin{lstlisting}[language=bash]
export MAKESYSPATH="/path/to/bmake-it/mk:${MAKESYSPATH:-/usr/share/mk}"
\end{lstlisting}
A project's top makefile then needs nothing but:
\begin{lstlisting}[language=bmake]
PARENT_WS=
.include "mk.workspace.mk"
\end{lstlisting}

\section{Checking the Setup}
\label{sec:setup-verify}

Build and run the bundled example, then run \texttt{Bmake It}'s own
test suite (about a hundred small workspaces exercising every feature;
about one to two minutes on a fast host):
\begin{lstlisting}[language=bash]
$ cd /path/to/bmake-it/examples/myworkspace
$ bmake && bmake run PROGRAM=hello
Hello, Bmake It!
$ cd /path/to/bmake-it
$ sh tests/harness/run-tests.sh                 # TOOLCHAIN=llvm
$ TOOLCHAIN=gcc sh tests/harness/run-tests.sh
\end{lstlisting}
On FreeBSD and NetBSD name the make under test, since the runner looks
for \texttt{bmake} by default: \verb|BMAKE=/usr/bin/make sh tests/harness/run-tests.sh|.
The summary line reads \verb|pass=N fail=0 skip=M|; a skipped case
names the tool or capability it lacks (OpenMP, ASan, a macOS-only
feature), so \verb|fail=0| is what matters.

\section{Languages and Scope}

\texttt{Bmake It} compiles C, C++, and lex/yacc grammar sources (which
themselves compile down to C/C++); no other language toolchain is
required\reqfoot{REQ-supported-languages}. It builds userspace binaries
and libraries only --- no kernel module or driver toolchain is
needed\reqfoot{REQ-userland-only-scope}.

%===============================================================
\chapter{Basic Tasks}
\label{ch:basic-usage}
%===============================================================

This chapter covers what you do every day: build, run, clean, install,
and lay out a workspace with its frameworks and modules. The examples
use \verb|examples/myworkspace| from the \texttt{Bmake It} tree: two
frameworks, \texttt{System} (a library, \texttt{calc}) and
\texttt{Hello} (a library, \texttt{greet}, and the program
\texttt{hello}, which links it).

\section{Everyday Commands}

Every command works at any level --- workspace root, framework or module
--- and acts on what lies beneath:
\begin{lstlisting}[language=bash]
$ cd examples/myworkspace
$ bmake                              # build everything for this host
$ bmake run PROGRAM=hello            # run a built program, environment set
Hello, Bmake It!
$ bmake run PROGRAM=bash             # an interactive shell in that environment
$ bmake help                         # the targets and variables valid here
$ bmake clean                        # remove this host's build output
$ bmake clean TARGET=all             # remove every target's build output
$ bmake install DESTDIR=/tmp/stage PREFIX=/usr/local
\end{lstlisting}
\begin{itemize}
\item \verb|bmake| builds each module completely, in dependency order,
  then copies its results up into its framework's \verb|build/<KEY>/|
  and the workspace's. \verb|<KEY>| is the target key ---
  \verb|freebsd-amd64|, \verb|macos-arm64|, \verb|linux-amd64-gcc| ---
  so builds for several targets live side by side
  (Chapter~\ref{ch:cross}).
\item \verb|bmake run| does not build; it runs any program with the
  workspace's (and each parent workspace's) \verb|bin/| first on
  \verb|PATH| and their \verb|lib/| on the library search path, from any
  directory of the workspace\reqfoot{REQ-run-build-environment-req}.
  \verb|ARGS="..."| passes arguments.
\item \verb|PROGRAM=bash| (or \texttt{sh}, \texttt{zsh}) opens a shell in
  which you call the programs you just built by name; your shell's
  start-up files still run, and cannot undo the build
  environment\reqfoot{REQ-run-shell-keeps-environment-req}.
\item \verb|install| copies an already-built target's \verb|bin/|,
  \verb|lib/| and \verb|share/| under \verb|$(DESTDIR)$(PREFIX)|; it
  refuses to run on a target that has not been built.
\end{itemize}

\section{What a Build Leaves Behind}

\begin{lstlisting}
myworkspace/
  build/<KEY>/bin/hello            consolidated results of the workspace
  build/<KEY>/lib/libgreet.so.1    (and the .so / .dylib / .dll forms)
  Hello/build/<KEY>/...            the framework's results
  Hello/hello.m/build/<KEY>/obj/   objects and dependency files
  Hello/hello.m/build/<KEY>/runs/<RUN_ID>/build.log
\end{lstlisting}
Every module keeps the log of each build under \verb|runs/<RUN_ID>/|
(\verb|runs/latest| is a copy of the newest), so a failure can be read
after the fact. When a workspace build fails, its last lines name each
failed module and the log to read.

\section{Adding a Module}

A module is a directory named \verb|<name>.m| inside a framework, with a
\verb|makefile| and a \verb|src/| directory; it is found automatically.
A library and a program that uses it:
\begin{lstlisting}[language=bmake]
# Hello/libgreet.m/makefile           # Hello/hello.m/makefile
LIB=greet                             PROG=hello
.include "mk.lib.mk"                  LIBS=greet
                                      .include "mk.prog.mk"
\end{lstlisting}
Sources in \verb|src/| are picked up without being listed. \verb|LIBS=|
names the libraries to link, and orders the build; headers come from
the include directories described in Section~\ref{sec:headers}.
The following sections describe each level in detail.

\section{Directory Layout at a Glance}

Every level of the hierarchy — workspace, framework, module — uses a
file literally named \verb|makefile| (not \verb|makefile.mk|), which
\verb|.include|s a role-specific helper file, mirroring the way real
BSD make's own \verb|bsd.prog.mk|/\verb|bsd.lib.mk| work\reqfoot{REQ-uniform-makefile-filename-req}:

\begin{center}
\begin{tabular}{lll}
\toprule
Level & Makefile contents (first line) & Key macro(s) \\
\midrule
Workspace & \verb|.include <mk.workspace.mk>| & \verb|PARENT_WS=| \\
Framework & \verb|.include <mk.framework.mk>| & \verb|PREREQS=| \\
Module (executable) & \verb|.include <mk.prog.mk>| & \verb|PROG=|, \verb|LIBS=| \\
Module (library) & \verb|.include <mk.lib.mk>| & \verb|LIB=|, \verb|LIB_SHARED=|, \verb|LIBS=| \\
\bottomrule
\end{tabular}
\end{center}

\section{Creating a Workspace}

A workspace is just a directory containing a \verb|makefile|:

\begin{lstlisting}[language=bmake]
.include <mk.workspace.mk>
PARENT_WS=/abs/path/to/parent-ws-1 /abs/path/to/parent-ws-2
\end{lstlisting}

\verb|PARENT_WS| is an ordered, space-delimited list of \textbf{absolute}
paths to parent workspaces\reqfoot{REQ-workspace-parent-macro-absolute-req}
— relative paths were explicitly considered and rejected as too
fragile. If left empty, the workspace has no parents and everything it
needs must live inside it. Frameworks inside the workspace are
auto-discovered: any immediate subdirectory containing a \verb|makefile|
that declares \verb|PREREQS=| is treated as a
framework\reqfoot{REQ-framework-discovery-signal-req}; there is no
explicit list to maintain.

\section{Creating a Framework}

A framework is a directory (any name — no special suffix, unlike
modules) containing its own \verb|makefile|:

\begin{lstlisting}[language=bmake]
.include <mk.framework.mk>
PREREQS=System
\end{lstlisting}

\verb|PREREQS=| is \textbf{mandatory even when empty}
(\verb|PREREQS=| with nothing after it is valid and means ``no
prerequisites'')\reqfoot{REQ-prereqs-mandatory-even-empty-req} — this
is not merely documentation, it is the literal signal the workspace
uses to recognize the directory as a framework at all. The list is
ordered, all entries are implicitly public (there is no per-entry
visibility qualifier the way real \texttt{mkmk}'s identity card
distinguished Public/Protected/Private), and \verb|Bmake It| does
\emph{not} validate the ordering or detect
cycles\reqfoot{REQ-framework-prereqs-macro-req}: an incorrectly
ordered or cyclic \verb|PREREQS| list simply surfaces later as an
ordinary ``header not found'' compile
error\reqfoot{REQ-prereqs-misorder-no-validation-req}.

A framework has three directories for hand-written headers,
described fully in Section~\ref{sec:headers}, and an optional
\verb|share/| directory for resources (Section~\ref{sec:resources}).

\section{Creating a Module}

A module's directory is always named \verb|NAME.m|; \verb|NAME| also
becomes the default output name if not overridden\reqfoot{REQ-module-dir-naming-convention, REQ-prog-lib-default-to-module-name-req}.
Whether \verb|NAME.m| and \verb|name.m| are distinct depends entirely
on the host filesystem's own case sensitivity — \texttt{Bmake It}
does not itself enforce or normalize case\reqfoot{REQ-module-name-case-sensitivity-req}.

\subsection*{An executable module}
\begin{lstlisting}[language=bmake]
.include <mk.prog.mk>
PROG=hello        # optional -- defaults to the directory name
LIBS=greet        # link-time only, space-delimited
\end{lstlisting}

\subsection*{A library module}
\begin{lstlisting}[language=bmake]
.include <mk.lib.mk>
LIB=greet             # optional -- defaults to the directory name
LIB_SHARED=YES        # default; LIB_SHARED=NO builds a static archive instead
LIBS=
\end{lstlisting}

\verb|LIB_SHARED| defaults to \verb|YES|;
setting it explicitly to \verb|NO| builds a static/archive library
instead\reqfoot{REQ-lib-shared-is-new-not-reused-req}. \textbf{Important, and
confirmed by empirical testing against real \texttt{bsd.lib.mk}}: this
\verb|YES|/\verb|NO| toggle is not itself a native BSD make mechanism
— real \verb|bsd.lib.mk| unconditionally builds a static archive
whenever \verb|LIB| is set, and additionally builds a shared library
only when \verb|SHLIB_MAJOR| is also present. \texttt{Bmake It}'s
\verb|mk.lib.mk| implements the \verb|LIB_SHARED| abstraction on top of
that native behavior\reqfoot{REQ-lib-shared-is-new-not-reused-req}.

A module's \verb|src/| directory is scanned automatically: every
source file physically present there is treated as compilation input,
with no \verb|SRCS=|-style list to maintain by
hand\reqfoot{REQ-module-src-auto-discovery}. \verb|.y| and \verb|.l|
(yacc and lex) files are compiled through the same automatic
mechanism, confirmed working via built-in suffix transformation rules
with zero explicit rule declarations\reqfoot{OBS-validation-yacc-lex-suffix-rules-confirmed}.

\verb|LIBS=| lists other modules or system libraries this module links
against. It is \textbf{purely a link-time instruction} and has no
effect whatsoever on header visibility, even for sibling modules in
the same framework\reqfoot{REQ-libs-macro-link-only-headers-via-prereqs-req}
— see Section~\ref{sec:headers} for how header visibility actually
works.

\section{Header Visibility}
\label{sec:headers}

Headers have exactly three visibility levels\reqfoot{REQ-three-level-header-visibility-req}:

\begin{center}
\begin{tabular}{lll}
\toprule
Level & Directory & Visible to \\
\midrule
Public & \verb|fw/include/| & Any framework declaring this one in \verb|PREREQS=| \\
Framework-internal & \verb|fw/local/include/| & All of this framework's own modules \\
Module-private & \verb|module.m/include/| & Only that module's own source files \\
\bottomrule
\end{tabular}
\end{center}

Header visibility is resolved \textbf{exclusively} through the
containing framework's \verb|PREREQS=| declaration — never through a
module's \verb|LIBS=|\reqfoot{REQ-headers-resolved-from-source-req}.
This is a genuine, deliberate design point worth internalizing: a
module can link against a library via \verb|LIBS=| while remaining
completely unable to see that library's headers, if the containing
frameworks aren't in a \verb|PREREQS=| relationship. Headers are
always read directly from source (\verb|include/| directories) —
never from build output — because headers are plain text and don't
need per-target staging the way compiled artifacts
do\reqfoot{REQ-headers-resolved-from-source-req}. The one exception is
\emph{generated} headers (from yacc/lex), covered in
Section~\ref{sec:generated-headers}.

\section{Building}

Run \verb|make| in a module directory to build just that module, in a
framework directory to build all its modules, or at the workspace root
to build everything. Modules and frameworks are auto-discovered by
scanning — modules via the \verb|.m| suffix, frameworks via the
\verb|makefile|+\verb|PREREQS=| signal\reqfoot{REQ-modules-and-frameworks-auto-discovered-req}.

The build strategy is \emph{fused}: each module compiles, generates
headers if applicable, and links in one pass — matching real
\verb|bsd.*.mk| idiom directly, rather than a global
compile-everything-then-link-everything
split\reqfoot{REQ-fused-build-per-module-full-dependency-order-req}.
Build order across frameworks follows the \verb|PREREQS=| dependency
graph; build order across sibling modules follows the \verb|LIBS=|
graph plus any consumed generated-header
dependency\reqfoot{REQ-framework-build-order-follows-prereqs-graph-req, REQ-fused-build-per-module-full-dependency-order-req}.
The concrete mechanism generating this order — confirmed by a working
prototype, not merely designed on paper — is described in
Section~\ref{sec:dep-order}.

\begin{lstlisting}[language=bash]
$ cd myworkspace/Hello
$ make                    # builds every module in Hello, in dependency order
$ cd hello.m
$ make                    # builds just this one module
\end{lstlisting}

\section{Cleaning and Installing}

\verb|make clean| removes \textbf{every} generated artifact for the
selected target — not just the compiled binaries, but also the
\verb|distrib/| packaging staging area, per-module \verb|.depend|
files, and the internal dependency-resolution
caches\reqfoot{REQ-clean-removes-all-derived-artifacts-req}. After
\verb|make clean TARGET=all|, the tree should be indistinguishable
from a fresh checkout.

\verb|make install DESTDIR=<staging-root> PREFIX=<final-path>| copies
the built \verb|bin|/\verb|lib|/\verb|share| content into
\verb|$(DESTDIR)$(PREFIX)|. \verb|DESTDIR| is confirmed genuinely
native to BSD make. \verb|PREFIX|, however, is \textbf{not} — testing
found zero references to it anywhere in real
\verb|bsd.own.mk|/\verb|bsd.prog.mk|/\verb|bsd.lib.mk|; real FreeBSD
base-system installs use hardcoded individual \verb|*DIR| variables
(\verb|BINDIR|, \verb|LIBDIR|, etc.) directly rather than a single
unifying \verb|PREFIX| the way GNU autotools or MacPorts do it.
\texttt{Bmake It}'s \verb|mk.prog.mk|/\verb|mk.lib.mk| derive those
\verb|*DIR| variables from \verb|PREFIX=| themselves\reqfoot{REQ-prefix-is-new-not-reused-req}.
It requires the target to already be built — it will not implicitly
trigger a build for you\reqfoot{REQ-install-requires-prebuilt-target-req}.
\textbf{Note}: confirmed by testing against both real FreeBSD and
NetBSD's own \verb|share/mk|, BSD make's \verb|install| does not
auto-create missing \verb|DESTDIR| parent
directories\reqfoot{OBS-validation-destdir-native-prefix-is-not} — the
destination tree must already exist.

\chapter{Advanced Tasks}
\label{ch:advanced}
%===============================================================

This chapter follows a real project, OpenRider (an outdoor-activity
viewer: C++20, Dear ImGui over GLFW and OpenGL, map tiles over libcurl,
plugins loaded at run time), through the things a project needs once it
outgrows the example: third-party code, project-wide rules, platform

\section{A Real Workspace: OpenRider}

\begin{lstlisting}
OpenRider/                       the workspace (PARENT_WS=, mk.workspace.mk)
  mk/pre.mk                      rules for every framework and module
  mk/pre.freebsd.mk, pre.win.mk, pre.llvm.mk   per platform / toolchain
  OpenRiderDependencies/         third-party code only   PREREQS=
    libglfw.m  libcurl.m  libtiff.m      imported from the system
    libimgui.m libimplot.m libsqlite3.m  fetched and compiled here
  OpenRider/                     the project's code      PREREQS=OpenRiderDependencies
    include/openrider/           the public plugin interface
    libcore.m  libapp.m  libmaptiles.m   libraries, with ATF tests
    openrider.m                  the program
    input_gpx.m  tiles_wmts.m ...        plugins (shared libraries)
    perf.tst  plugin_check.tst           test modules
\end{lstlisting}
Third-party code lives in a framework of its own, so the project's
framework depends on it through \verb|PREREQS=| and the build order
follows. The program's makefile is a few lines:
\begin{lstlisting}[language=bmake]
# OpenRider/openrider.m/makefile
PROG=openrider
LIBS=app core maptiles implot imgui glfw
.include "mk.prog.mk"
\end{lstlisting}
\verb|LIBS=| mixes the project's own libraries and imported ones: an
imported library is an ordinary module, linked the same
way\reqfoot{REQ-imported-libraries-are-ordinary-modules-req}.

\section{Using a Library From the System}
\label{sec:openrider-imports}

\begin{lstlisting}[language=bmake]
# OpenRiderDependencies/libglfw.m/makefile
LIB=glfw
IMPORT=pkg:glfw3          # resolved with pkg-config
REQUIRES=glfw3            # a clear error, before building, if it is missing
IMPORT_HEADERS=GLFW       # staged into the framework's build/<KEY>/include
.include "mk.lib.mk"
\end{lstlisting}
The import stages the library's headers and files into the build tree,
so the rest of the workspace sees them like those of a compiled
library. A header-only package says \verb|IMPORT_LIB=none|. Staging is
skipped while nothing changed --- and done again if a staged file has
gone missing, naming it\reqfoot{REQ-staging-skip-checks-outputs-req}.
For a cross build, pkg-config is asked about the target's sysroot,
never the build host's packages (Chapter~\ref{ch:cross}).

\section{Fetching and Compiling Third-Party Sources}

\begin{lstlisting}[language=bmake]
# OpenRiderDependencies/libimgui.m/makefile
LIB=imgui
IMPORT=fetch:imgui
FETCH_URL=https://github.com/ocornut/imgui/archive/refs/tags/v1.92.9b.tar.gz
SRCS=imgui.cpp imgui_draw.cpp imgui_tables.cpp imgui_widgets.cpp \
     backends/imgui_impl_glfw.cpp backends/imgui_impl_opengl3.cpp
IMPORT_HEADERS=imgui.h imconfig.h backends/imgui_impl_glfw.h ...
LIB_SHARED=NO             # a static archive, linked into its users
WARN=none                 # their warnings are not ours (Chapter on linting)
LIBS=glfw                 # the GLFW backend needs GLFW's headers first
.include "mk.lib.mk"
\end{lstlisting}
The archive is downloaded once into the module's \verb|distfiles/|,
checked against the committed \verb|distinfo|, extracted, patched
(\verb|FETCH_PATCHES=|) and compiled through the ordinary \verb|SRCS=|
pipeline; nothing of it is committed. Write \verb|distinfo| when you
add or update the source:
\begin{lstlisting}[language=bash]
$ curl -fLO https://github.com/ocornut/imgui/archive/refs/tags/v1.92.9b.tar.gz
$ printf 'SHA256 (%s) = %s\n' v1.92.9b.tar.gz \
      "$(sha256sum v1.92.9b.tar.gz | cut -d' ' -f1)" > libimgui.m/distinfo
\end{lstlisting}
A project with its own build system is built with it instead:
\verb|FETCH_BUILD=cmake| (or \texttt{autotools}, \texttt{meson},
\texttt{custom} with \verb|FETCH_BUILD_CMD=|), and installed into the
module's build tree.

\section{Project-Wide Rules: Hook Files}
\label{sec:hooks}

A level's \verb|mk/| directory --- workspace, framework or module ---
may hold hook files, read in this order: \verb|pre.mk|, then
\verb|pre.<toolchain>.mk|, \verb|pre.<os>.mk| and
\verb|pre.<os>_<arch>.mk|, before the role file's own defaults; the
same names with \verb|local| instead of \verb|pre| after them. Every
matching level applies, outer to
inner\reqfoot{REQ-local-mk-hook-files-and-cascade-order-req}. OpenRider's:
\begin{lstlisting}[language=bmake]
# mk/pre.mk -- every module of the workspace
CXXSTD = c++20
CXXFLAGS += -fno-exceptions -fno-rtti

# mk/pre.freebsd.mk -- FreeBSD only
CFLAGS += -idirafter /usr/local/include   # ports' headers, after the staged ones
CXXFLAGS += -idirafter /usr/local/include
LDFLAGS += -pthread

# mk/pre.llvm.mk -- clang only
CXXFLAGS += -include ${.PARSEDIR}/include/openrider_compat.h
\end{lstlisting}
Hook files are where a project keeps what differs per platform, so
that its module makefiles stay free of conditionals. A per-host value
--- a library's location on one developer's machine --- belongs in a
\verb|local.mk| that is not committed.

\section{Documentation}

\begin{lstlisting}[language=bmake]
# OpenRider/makefile (the framework)
PREREQS=OpenRiderDependencies
DOCS=yes
DOC_INPUT_EXTRA=local/include openrider.m/src ...   # beyond include/
DOC_WARN_IF_UNDOCUMENTED=YES
.include "mk.framework.mk"
\end{lstlisting}
\verb|bmake docs| runs Doxygen over the framework (from a framework) or
over every framework plus an index page (from the workspace root);
\verb|DOCS=no| leaves a framework out, as OpenRider does for its
third-party one.

\section{Workspace Builds, Reports and Continuous Integration}

\begin{lstlisting}[language=bash]
$ bmake REPORT=yes                 # HTML dashboard of every module's build
$ bmake test REPORT=yes            # the same for the tests
$ bmake FAIL_FAST=yes              # stop at the first failing module
$ bmake RUN_ID=ci-4821             # name the run (logs, reports)
\end{lstlisting}
By default a failing module does not stop the others; the exit status
is non-zero if any failed, and the final lines list each failure with
its log. A framework whose prerequisite failed is skipped, with one
line saying why, rather than failing again with a cascade of missing
headers. OpenRider's continuous integration is three steps after
installing the packages (Chapter~\ref{ch:setup}):
\begin{lstlisting}
env:
  MAKESYSPATH: ${{ github.workspace }}/.bmake-it/mk:/opt/local/share/mk
steps:
  - run: bmake            # build
  - run: bmake test       # test; JUnit XML under */build/*/runs/*/test-results.xml
\end{lstlisting}
\texttt{Bmake It} itself is checked out next to the sources, in a hidden
directory, so that the workspace does not take it for a framework.

\section{Resource Files}
\label{sec:resources}

Both modules and frameworks may carry a \verb|share/| directory for
non-source runtime data\reqfoot{REQ-resource-file-model}. Resources
support per-target variants via a three-level fallback hierarchy:

\begin{center}
\begin{tabular}{ll}
\toprule
Directory & Applies to \\
\midrule
\verb|share/common/| & Every target, unconditionally \\
\verb|share/<os>/| & All architectures of one OS (e.g.\ \verb|share/freebsd/|) \\
\verb|share/<os>_<arch>/| & One specific OS+architecture pairing \\
\bottomrule
\end{tabular}
\end{center}

Staging is a \textbf{layered overlay copy}, not a
pick-one-directory selection: \verb|common/| copies first, then
\verb|<os>/| on top of it (overwriting same-named files), then
\verb|<os>_<arch>/| on top of that\reqfoot{REQ-share-overlay-copy-order}.
Files unique to any one layer survive regardless; only files present
at multiple layers end up as the most specific version. Unlike the
compiled-artifact target key, the resource fallback key is
\textbf{OS+architecture only} — toolchain never affects which resource
variant is selected\reqfoot{REQ-share-dir-fallback-hierarchy}.

\section{Generated Headers}
\label{sec:generated-headers}

Headers produced by tooling (yacc/lex output, for
example) don't exist until the build runs, so they can't live in
\verb|include/| as source. They are, by default, \textbf{private} to
the generating module, landing in
\verb|module/build/<KEY>/include/|\reqfoot{REQ-generated-headers-in-build-tree-req}.

A module promotes specific generated headers to public visibility via
\verb|INCL=|:
\begin{lstlisting}[language=bmake]
INCL=grammar.h
\end{lstlisting}
On build, the listed headers are copied up into
\verb|fw/build/<KEY>/include/| — a framework-level directory
containing \textbf{only} promoted generated headers, never hand-written
ones\reqfoot{REQ-incl-macro-promotes-generated-headers-req}. When
another framework resolves a \verb|PREREQS|-declared framework's
headers, it checks \emph{both} that framework's \verb|include/|
(hand-written) \emph{and} its \verb|build/<KEY>/include/| (promoted
generated) — the one deliberate, scoped exception to ``never consult
build output for headers''\reqfoot{REQ-generated-headers-in-build-tree-req}.
There is no workspace-level equivalent: a workspace-wide generated-header
directory is never consulted at compile time, only during packaging.

\section{Versioned Shared Libraries}

Shared-library versioning reuses \verb|SHLIB_MAJOR|/\verb|SHLIB_MINOR|
directly, translated per platform by \verb|mk.lib.mk|:

\begin{center}
\begin{tabular}{ll}
\toprule
Platform & Emission \\
\midrule
FreeBSD / Linux (ELF) & \verb|libfoo.so.MAJOR[.MINOR]| + standard symlink chain \\
macOS (Mach-O) & \verb|libfoo.MAJOR.dylib| + symlink + linker \verb|-compatibility_version|/\verb|-current_version| \\
\bottomrule
\end{tabular}
\end{center}

A single author-facing macro pair drives both platform-appropriate
emission strategies, since embedded Mach-O version metadata (not just
the filename) is macOS's actual ABI-compatibility
mechanism\reqfoot{REQ-shlib-major-minor-cross-platform-emission-req}.
This specific translation for macOS remains \textbf{unverified against
real MacPorts \texttt{bsdmake}} — no macOS environment was available
during this project's validation pass, and real \verb|bsd.lib.mk|'s
shared-library logic was designed primarily for ELF; MacPorts'
\verb|bsdmake| may have no Mach-O awareness at all, in which case this
logic needs to be written entirely inside \texttt{Bmake It}'s own
\verb|mk.lib.mk|. \textbf{[open]}

\section{Packaging}

Packaging is driven by separate named \verb|make| targets, one per
format, rather than a single parameterized
target\reqfoot{REQ-packaging-per-format-targets-req}: confirmed target
names so far are \verb|port| (BSD ports-style source recipe) and
\verb|pkg| (macOS-style binary package), with \verb|deb|/\verb|rpm|
following the same pattern. Every binary-package target (\verb|pkg|,
\verb|deb|, \verb|rpm|) stages a \verb|distrib/<KEY>/| directory — the
same target-key scheme as \verb|build/| — by internally invoking the
equivalent of \verb|install DESTDIR=distrib/<KEY>|, reusing the install
machinery rather than a separate copy
mechanism\reqfoot{REQ-packaging-invokes-install-into-distrib-req}.

\verb|make port| is \textbf{categorically different}: it produces a
source-based, BSD-ports-style recipe (port \verb|Makefile|,
\verb|distinfo|, patches, \verb|pkg-plist|) for the ports system to
fetch and build itself — no pre-built binary is ever staged or
embedded\reqfoot{REQ-port-target-is-source-recipe-not-binary-package-req}.
Its exact generation mechanism is deferred to a later
phase\reqfoot{REQ-make-port-deferred-req}. \textbf{[open]}

\section{Running a Built Program}

\verb|bmake run PROGRAM=<name> ARGS="<args>"| runs \emph{any} program
--- one you built, a shell, a debugger, a profiler --- through the
build environment, from any directory of the workspace (it walks up to
the root)\reqfoot{REQ-run-build-environment-req}. The environment is
inherited and prepended to, never replaced:
\begin{center}
\begin{tabular}{ll}
\toprule
Variable & Value \\
\midrule
\verb|PATH| & workspace \verb|bin|, each \verb|PARENT_WS| \verb|bin|, then yours \\
library path & workspace \verb|lib|, each \verb|PARENT_WS| \verb|lib|, then yours \\
\verb|BMK_BINDIR|, \verb|BMK_LIBDIR|, \verb|BMK_SHAREDIR| & the same chains \\
\verb|BMK_TARGET|, \verb|BMK_LIBVAR| & the target key, the library variable's name \\
\bottomrule
\end{tabular}
\end{center}
The library path is \verb|LD_LIBRARY_PATH|, \verb|DYLD_LIBRARY_PATH| on
macOS and \verb|PATH| itself on Windows. A program found nowhere on
that \verb|PATH| is an error naming the chain; a non-zero exit status
fails the make. Examples:
\begin{lstlisting}[language=bash]
$ bmake run PROGRAM=openrider ARGS="--snapshot out.png"
$ bmake run PROGRAM=gdb ARGS="--args openrider -v"   # debug with the libraries found
$ bmake run PROGRAM=bash                             # call programs by name
\end{lstlisting}
It mirrors \texttt{mkmk}'s \texttt{mkrun}, adapted to
\texttt{Bmake It}'s own \verb|build/<KEY>/| layout.

\section{Self-Documentation: \texttt{make help}}

\verb|make help|, run at any level, lists every valid target and
variable applicable there, along with a description and — where
relevant — the set of valid values (for example,
\verb!LIB_SHARED=YES|NO!). Each role-specific \verb|mk.*.mk| file is
responsible for documenting its own contribution, so the aggregate
output always matches exactly what's actually
\verb|.include|d at that level\reqfoot{REQ-help-target-req}.

\section{Convenience Targets}

Two small convenience targets exist purely to reduce hand-editing
error, without introducing any resolution or search behavior (they do
\textbf{not} reopen the earlier rejection of
\texttt{mkGetPreq}/\texttt{mkCopyPreq}):

\begin{lstlisting}[language=bash]
$ make add-prereq FW=System     # appends System to PREREQS= in the current framework
$ make add-parent WS=/abs/path  # appends /abs/path to PARENT_WS=
\end{lstlisting}
\reqfoot{REQ-add-prereq-add-parent-convenience-targets-req}

\section{Dependency-Order Generation}
\label{sec:dep-order}

Since real \verb|bsd.subdir.mk| has no concept of a topological build
order — it simply processes whatever \verb|SUBDIR| list it's given —
\texttt{Bmake It} generates that order itself, in a mechanism
confirmed by a working, tested prototype rather than only designed on
paper\reqfoot{REQ-dep-order-generation-mechanism-req}:

\begin{enumerate}
\item Discover \verb|.m| module directories by scanning.
\item Query each module's \verb|LIBS=| \emph{in isolation}, via
  \verb|bmake -f <dir>/makefile -V LIBS| — confirmed to read the
  variable without triggering a build.
\item Topologically sort (Kahn's algorithm), silently ignoring any
  \verb|LIBS=| entry that isn't a locally-discovered module (such
  references are resolved via the framework's \verb|PREREQS=|
  instead, not module-level ordering).
\item Emit the sorted order to a generated \verb|.mk| fragment
  (\verb|SUBDIR=modA.m modB.m ...|), \verb|.include|d before
  \verb|.include <bsd.subdir.mk>|.
\end{enumerate}

This was tested on a real four-module dependency chain
(\texttt{A}$\leftarrow$\texttt{B}$\leftarrow$\texttt{C}$\leftarrow$\texttt{D},
with \texttt{C} depending on both \texttt{A} and \texttt{B}) and built
in the correct order every time; a genuine cycle
(\texttt{X}$\leftrightarrow$\texttt{Y}) was confirmed to fail loudly
with a clear diagnostic rather than hanging or silently producing a
broken order. The identical mechanism generalizes directly to
workspace-level framework ordering, querying \verb|PREREQS=| instead
of \verb|LIBS=|.

\subsection*{The \texttt{order} Target}
\label{sec:order-target}

This generation step is formalized as its own explicit,
workspace-level target: \verb|make order| performs a \textbf{blank
run} — no compilation, no linking — scanning every framework and every
module across the whole workspace, resolving the complete dependency
graph (framework order via \verb|PREREQS=|, and each framework's
module order via \verb|LIBS=|) in one pass, and writing the result to
a cache\reqfoot{REQ-order-target-blank-run-req}. The default
\verb|make| target then reads that cache rather than re-resolving
order inline on every invocation.

The order cache is treated as an \emph{implicit prerequisite} of the
default build, not an optional manual step: if it is missing or
detected stale, \verb|make| regenerates it automatically before
proceeding, so a fresh checkout builds correctly with plain
\verb|make| and no separate mandatory
invocation\reqfoot{REQ-order-cache-auto-triggered-req}. \verb|make order|
remains independently runnable on its own, for inspecting the
resolved build order without triggering an actual build.

As a defensive safety net on top of this — since the order cache
\emph{should} always be correct, but a stale cache, a partial manual
build, or a genuine bug could in principle defeat it — immediately
before invoking the linker for a module, \texttt{Bmake It} verifies
that every \verb|LIBS=| entry's build artifact actually exists. A
missing one produces an explicit, specific error (\emph{``cannot link
\texttt{hello}: prerequisite library \texttt{greet} (from
\texttt{LIBS=}) has not been built yet''}) rather than the linker's
own generic \emph{``cannot find -lgreet''}\reqfoot{REQ-link-time-not-yet-built-guard-req}.
This should essentially never fire in ordinary operation; its value is
a clear diagnostic on the rare occasion something has genuinely gone
wrong.

\section{Caching}

Two distinct caches, both modeled on real BSD make's own
\verb|.depend| idiom (a generated file, regenerated via an explicit or
detected-stale trigger, consumed via \verb|.include| on subsequent
runs)\reqfoot{REQ-prereqs-resolution-cached-like-depend-req}:

\begin{enumerate}
\item \textbf{\texttt{PARENT\_WS}/\texttt{PREREQS} resolution cache} —
  workspace/framework-level: caches header search paths and build
  order so they aren't re-walked on every invocation. Formalized as an
  explicit workspace-level target, \verb|make order| — described in
  Section~\ref{sec:order-target}.
\item \textbf{Per-module \texttt{.depend}} — file-level,
  \texttt{mkdep}-style: which source files include which headers
  (transitively), so touching a header only triggers recompilation of
  the affected \verb|.o| files, not a full module rebuild.
\end{enumerate}

\textbf{The per-module case has a genuinely interesting empirical
story, worth telling in full rather than just stating the conclusion.}
An initial test ran the separate \verb|make depend| target against
real FreeBSD \verb|share/mk| and found it nearly useless — no header
tracking, just one link-level line. That looked like confirmation the
mechanism needed custom shell-script wiring. A closer look reversed
that conclusion: every ordinary compile already includes
\verb|-MD -MF.depend.<obj>| — \verb|bsd.sys.mk| wires the
\emph{compiler's own} native dependency-generation flag into every
build, with no separate step at all, and this was confirmed correct
end-to-end (touching a shared header triggered recompilation of
exactly the right objects). But a further cross-check against
NetBSD's own bundled \verb|mk| set found \emph{zero} such wiring there
— plain compiles, no dependency flags, no rebuild when a header
changed. So the working mechanism is real, but specific to FreeBSD's
own actual \verb|bsd.sys.mk|, not a general BSD-make-family property.
Since macOS (via MacPorts) is a phase-1 host and MacPorts' own
\verb|bsdmake| could not be tested in this pass, whether it includes
equivalent wiring was left genuinely unknown\reqfoot{REQ-md-dependency-tracking-freebsd-specific-req}
at the time.

\textbf{Resolved 2026-09-24, and the MacPorts question turned out to be
moot.} Read directly (on a real MacPorts host this time): \verb|mk.prog.mk|/
\verb|mk.lib.mk| never \verb|.include| \verb|bsd.sys.mk|, \verb|bsd.prog.mk|,
\verb|bsd.lib.mk|, or any other real \verb|bsd.*.mk| file at all — only
Bmake It's own \verb|mk.*.mk| role files, each defining fully explicit
\verb|target: source| compile rules with hand-written recipes. So real
\verb|bsd.sys.mk|'s own \verb|-MD| wiring, confirmed or not on any given
host, was never reachable from Bmake It's own compiled objects in the
first place — the question wasn't "does MacPorts have it," it was "does
Bmake It's architecture ever ask." It doesn't. The fallback mentioned
above (add the flags directly) is what was actually built: every gcc/clang
compile recipe now passes \verb|-MMD -MP -MF <obj>.d| itself, and each
object's own \verb|.d| file is conditionally \verb|.include|d on the next
build\reqfoot{REQ-header-dependency-tracking-req}. This is new,
project-owned wiring, not reused \verb|bsd.sys.mk| behavior — confirmed
end-to-end on this MacPorts host: a private header, and a framework-public
header reached only via \verb|PREREQS=| (not the consuming module's own
\verb|src/|), each correctly trigger exactly the affected object to
recompile, and a no-op rebuild recompiles nothing. Under
\verb|TOOLCHAIN=msvc| the \verb|cl.exe| wrapper writes the same dependency
file from \verb|cl.exe|'s own \verb|/showIncludes| notes, leaving out the
toolset's and the Windows SDK's headers as \verb|-MMD| leaves out system
headers.

Exact generated filenames, staleness-detection mechanisms, and
regeneration triggers for the \verb|PARENT_WS|/\verb|PREREQS| cache
are deliberately deferred until real \verb|bsd.*.mk| infrastructure
can be checked hands-on for what it already
provides\reqfoot{OBS-cache-mechanism-needs-empirical-check}. \textbf{[open]}

%===============================================================
\chapter{Cross-Platform Compilation and Testing}
\label{ch:cross}
%===============================================================

One source tree builds for several targets, each into its own
\verb|build/<KEY>/|, without a separate checkout or configuration step.
This chapter shows how to choose the target, cross-compile, build
Windows programs, and run the tests of a target the build host cannot
run itself.

\section{The Target Key}

The target key has the shape \verb|<os>-<arch>[-<toolchain>][-<abi>]|,
each bracketed segment omitted when it is that platform's
default\reqfoot{REQ-target-key-omit-defaults-req}:
\begin{center}
\begin{tabular}{lll}
\toprule
Segment & Default (omitted) & Shown when non-default \\
\midrule
Toolchain & \verb|llvm| & \verb|gcc|, \verb|msvc| \\
ABI & \verb|glibc| (linux); \verb|msvc| (win) & \verb|musl|; \verb|cygwin|, \verb|mingw| \\
\bottomrule
\end{tabular}
\end{center}
Examples: \verb|freebsd-amd64|, \verb|macos-arm64-gcc|,
\verb|linux-amd64-musl|, \verb|win-amd64-cygwin|, \verb|win-amd64-gcc-mingw|,
\verb|win-amd64-msvc|. On Windows the ABI is read from the compiler
itself (\verb|-dumpmachine|), never assumed.

\section{Choosing the Target}

\begin{lstlisting}[language=bash]
$ bmake                                         # this host, LLVM
$ bmake TOOLCHAIN=gcc                           # this host, GCC
$ bmake TARGET=freebsd TARGET_ARCH=amd64        # another OS and architecture
$ bmake TARGET=linux TARGET_ARCH=arm64 ABI=musl
\end{lstlisting}
\verb|TARGET=| and \verb|TARGET_ARCH=| reuse BSD make's own cross-build
variable names; \verb|TOOLCHAIN=| and \verb|ABI=| are \texttt{Bmake It}'s.
In BSD make itself these names are only \emph{data}: testing against
real FreeBSD \verb|share/mk| showed \verb|TARGET_ARCH=arm64| on an
\texttt{amd64} host still producing an \texttt{x86-64} binary. So
\verb|mk.toolchain.<name>.mk| maps each (\verb|TARGET|,
\verb|TARGET_ARCH|, \verb|TOOLCHAIN|) to concrete compiler flags
itself\reqfoot{REQ-target-arch-toolchain-selection-is-custom-req, OBS-validation-cross-compile-is-external-orchestration-everywhere}.
An ABI the target does not have (\verb|ABI=mingw TARGET=linux|) is an
error, not a strange key.

\section{Cross-Compiling for Linux, FreeBSD, NetBSD and macOS}

Cross-compiling uses LLVM (one compiler for every target; GCC never
cross-compiles here) and a \emph{sysroot}: the target system's headers
and libraries, given in a variable per OS:
\begin{center}
\begin{tabular}{ll}
\toprule
Target & Variable and content \\
\midrule
Linux & \verb|BMK_LINUX_SYSROOT|: \verb|usr/include|, \verb|usr/lib/<multiarch>|, \verb|lib/<multiarch>| \\
FreeBSD & \verb|BMK_FREEBSD_SYSROOT|: \verb|usr/include|, \verb|usr/lib|, \verb|lib| from \verb|base.txz| \\
NetBSD & \verb|BMK_NETBSD_SYSROOT|: \verb|usr/include|, \verb|usr/lib|, \verb|libexec/ld.elf_so| \\
macOS & \verb|BMK_MACOS_SYSROOT|: your own \verb|MacOSX.sdk| (not redistributable) \\
\bottomrule
\end{tabular}
\end{center}
The scripts under \verb|tests/harness/fetch/| make them as tar files
from official release artifacts --- \verb|build-sysroot-freebsd.sh|
(\verb|base.txz|), \verb|build-sysroot-netbsd.sh| (the release sets),
\verb|build-sysroot-linux.sh| (a container; a project image with its
\verb|-dev| packages gives their libraries and \verb|.pc| files too) and
\verb|build-sysroot-macos.sh| (your Xcode's SDK). Extract a Linux
sysroot on a case-sensitive filesystem: kernel headers differ only by
case. Then, for example from a Mac:
\begin{lstlisting}[language=bash]
$ bmake TARGET=freebsd TARGET_ARCH=amd64 BMK_FREEBSD_SYSROOT=$HOME/sysroots/freebsd-amd64
$ file build/freebsd-amd64/bin/openrider
build/freebsd-amd64/bin/openrider: ELF 64-bit LSB executable, x86-64, ... FreeBSD 15.1
\end{lstlisting}
Keep the sysroot out of the command line with a hook file
(Section~\ref{sec:hooks}), here \verb|mk/local.freebsd_amd64.mk|:
\begin{lstlisting}[language=bmake]
BMK_FREEBSD_SYSROOT = /home/me/sysroots/freebsd-amd64
\end{lstlisting}
Libraries imported with \verb|IMPORT=pkg:| and \verb|REQUIRES=| are
looked up in the target's sysroot (Linux's multiarch
\verb|pkgconfig|, FreeBSD's \verb|usr/local/libdata/pkgconfig|,
NetBSD's \verb|usr/pkg/lib/pkgconfig|), never on the build host; a
package missing there is an error naming the sysroot.

\section{Windows Programs}

From a Cygwin shell, three kinds of output, each with its own key:
\begin{lstlisting}[language=bash]
$ bmake                          # Cygwin programs (cygwin1.dll)  build/win-amd64-cygwin/
$ bmake ABI=mingw                # native, mingw-w64 (clang)      build/win-amd64-mingw/
$ bmake TOOLCHAIN=gcc ABI=mingw  # native, mingw-w64 (gcc)        build/win-amd64-gcc-mingw/
$ bmake TOOLCHAIN=msvc           # native, MSVC                   build/win-amd64-msvc/
$ bmake TOOLCHAIN=msvc BMK_EWDK_ROOT='F:\'   # MSVC from a mounted EWDK
\end{lstlisting}
Module makefiles do not change between them. Under MSVC a shared
library needs no \verb|__declspec(dllexport)|: its export list is
generated from its objects, so it gets an import library as on every
other toolchain\reqfoot{REQ-msvc-shared-lib-export-req}; a \emph{data}
symbol used from another module still needs \verb|dllimport| on the
user's side (\verb|include/bmk_export.h|). Header dependencies are
tracked under MSVC as elsewhere. \verb|bmake run| puts the mingw-w64
runtime DLLs on \verb|PATH| for mingw programs.

\section{Running and Testing What You Cross-Built}

\verb|bmake test| runs Kyua on the build host. For a target the host
cannot run, name a \emph{test runner}; \verb|bmake test| then ships the
test programs, the libraries they load and the \verb|share/| data to it,
runs them there, and brings the JUnit report back to the usual place.
The exit status is the tests'\reqfoot{REQ-cross-test-runner-req}.
\begin{lstlisting}[language=bash]
# a FreeBSD machine (or VM) over ssh
$ bmake test TARGET=freebsd TARGET_ARCH=arm64 \
      TEST_RUNNER.freebsd-arm64=ssh:root@localhost:2226
# Linux amd64 tests in an emulated container, from an arm64 host; the image
# must hold kyua and atf (here the one the project's own matrix builds)
$ bmake test TARGET=linux TARGET_ARCH=amd64 \
      TEST_RUNNER.linux-amd64=docker:bmk/linux-glibc:amd64@linux/amd64
# the host runs the foreign binaries itself (qemu-user registered with binfmt)
$ bmake test TARGET=linux TARGET_ARCH=amd64 TEST_RUNNER=local
\end{lstlisting}
\begin{center}
\begin{tabular}{ll}
\toprule
Runner & Runs the tests \\
\midrule
\verb|ssh:[user@]host[:port]| & on that machine (\verb|BMK_SSH_OPTS| gives ssh its key and options) \\
\verb|docker:<image>[@<platform>]| & in a throw-away container \\
\verb|cmd:<program>| & wherever \verb|<program> <staged-dir>| runs them (a board, a custom VM) \\
\verb|local| & here; for Linux, with \verb|QEMU_LD_PREFIX| set to the sysroot \\
\bottomrule
\end{tabular}
\end{center}
\verb|TEST_RUNNER| names one runner for every target; the per-target
\verb|TEST_RUNNER.<os>-<arch>| wins. With no runner for a foreign
target, \verb|bmake test| stops before building and names the variables
to set: target binaries are never run on the wrong machine silently.
OpenRider's 209 tests pass for \verb|linux-amd64| on a
\verb|linux-arm64| host with \verb|TEST_RUNNER=local|.

\section{Several Targets, One Run}

\begin{lstlisting}[language=bash]
$ for tc in llvm gcc; do bmake test TOOLCHAIN=$tc RUN_ID=ci-4821 REPORT=yes; done
$ ls test-report/ci-4821/
macos-arm64/  macos-arm64-gcc/
\end{lstlisting}
Each key keeps its own outputs, logs and dashboard under one
\verb|RUN_ID|. \verb|bmake clean| removes the current key's output only;
\verb|bmake clean TARGET=all| removes every key's.

\section{The Project's Own Test Matrix}

\texttt{Bmake It} tests itself on every platform it can reach with
\verb|tests/harness/matrix.sh|: the suite natively on each platform
(Linux in containers, FreeBSD and NetBSD in QEMU guests --- accelerated
with hvf on macOS, KVM on Linux, WHPX on Windows --- macOS in a VM,
Windows under Cygwin with every toolchain, and the BSD machine running
the matrix itself), plus cross cells that build on one platform and run
on another. Images, sysroots, guest packages and results live in
\verb|BMK_CACHE| (a directory such as \verb|bsk/cache|); guests'
packages are kept there so that a guest is rebuilt without the
network\reqfoot{REQ-guest-packages-from-cache-req}. A cell that cannot
run on the current host is reported \emph{blocked}, with the reason.
\begin{lstlisting}[language=bash]
$ cd tests/harness
$ export BMK_CACHE=/path/to/bsk/cache
$ sh matrix.sh list
$ sh matrix.sh run 'native-freebsd_host-*'   # on a FreeBSD machine
$ sh matrix.sh report
\end{lstlisting}
See \verb|tests/README.md| for the cells, the guests and the cache
layout.

%===============================================================
\chapter{Testing}
\label{ch:testing}
%===============================================================

\verb|bmake test| builds what is needed, runs a module's (or every
module's) tests through Kyua, writes a JUnit report, and fails if any
test fails\reqfoot{REQ-unit-test-feature-for-built-software-req}. Tests
are written with ATF, in C, C++ or shell; Kyua runs them alike.

\section{Unit Tests in a Module}

A module names its tests; their sources are \verb|tests/<name>.c|,
\verb|tests/<name>.cpp| or \verb|tests/<name>.sh|:
\begin{lstlisting}[language=bmake]
# OpenRider/libcore.m/makefile
LIB=core
LIBS=openrider_sdk cjson
TESTS_CXX=types_test library_test log_test plugins_test
.include "mk.lib.mk"
\end{lstlisting}
\begin{lstlisting}[language=C++]
// OpenRider/libcore.m/tests/types_test.cpp
#include <atf-c++.hpp>
#include "core/type_catalog.h"

ATF_TEST_CASE_WITHOUT_HEAD(source_mapping_wins_over_device_type);
ATF_TEST_CASE_BODY(source_mapping_wins_over_device_type)
{
    const core::TypeCatalog c = Catalog();
    const core::ActivityType t =
        c.Resolve("garmin_connect", "backcountry_skiing", "running", "trail");
    ATF_REQUIRE_EQ(t.Key(), "alpine_skiing/backcountry");
}

ATF_INIT_TEST_CASES(tcs) { ATF_ADD_TEST_CASE(tcs, source_mapping_wins_over_device_type); }
\end{lstlisting}
A test of a library links the library; a test of a program links the
program's objects, without its \verb|main|. \verb|bmake test| builds
the module first, so a test always runs against the current code.

\section{Running Tests}

\begin{lstlisting}[language=bash]
$ bmake test                          # this module, framework or workspace
$ bmake test TEST=types_test          # one test program
$ bmake test FW=OpenRider             # one framework, from the workspace root
$ bmake test REPORT=yes               # plus HTML reports and a dashboard
$ bmake test FAIL_FAST=yes            # stop at the first failing module
\end{lstlisting}
\begin{lstlisting}
types_test:source_mapping_wins_over_device_type  ->  passed  [0.004s]
...
===> test results: build/macos-arm64/runs/20261029-101530-4242/test-results.xml
\end{lstlisting}
The JUnit file is written whether the tests pass or not (a failure is
when it matters most); Kyua's own store keeps every run's raw output
(\verb|kyua report --verbose|).

\section{Test Modules (\texttt{.tst})}

Tests that exercise several libraries together, the installed programs,
or scripts live in a \verb|<name>.tst| module: built by a plain
\verb|bmake| (a test's compile error shows at build time) but never
copied up, installed or packaged.
\begin{lstlisting}
plugin_check.tst/
  makefile        TEST_PROG=... or PROG=<utility>, LIBS=...  .include "mk.tst.mk"
  src/            compiled sources
  testcases/*.sh  each script is an atf-sh test, found automatically
\end{lstlisting}
\begin{lstlisting}[language=bmake]
# OpenRider/perf.tst/makefile
TEST_PROG=perf_test
LIBS=app core maptiles reproj
.include "mk.tst.mk"
\end{lstlisting}
\verb|TEST_PROG=| builds an ATF test program; \verb|PROG=| builds a
utility the scripts call (with both, \verb|TEST_SRCS=| says which
sources are the test's). The scripts see the build results: the
framework's and workspace's \verb|bin/| on \verb|PATH|, and
\verb|BMK_SHAREDIR|.

\section{Sanitizers}

\begin{lstlisting}[language=bash]
$ bmake test SANITIZE=address,undefined
$ bmake run PROGRAM=openrider SANITIZE=address   # rebuild first: bmake SANITIZE=address
\end{lstlisting}
\verb|SANITIZE=| (\texttt{address}, \texttt{undefined}, \texttt{thread},
\texttt{memory}, \texttt{leak}) instruments compile and link everywhere
in the workspace; changing it rebuilds what it affects. An undefined
behaviour aborts at its first occurrence instead of being logged and
survived. Incompatible pairs (\texttt{address} with \texttt{thread} or
\texttt{memory}) are an error, and MSVC offers \texttt{address}
only\reqfoot{REQ-sanitizer-support-req}. The bundled example carries
deliberate fixtures: \verb|libcalc| writes one element past its buffer,
which \verb|SANITIZE=address| catches in \verb|calc_test|.

\section{Tests on Other Targets and on Windows}

A foreign target's tests run on a test runner (Chapter~\ref{ch:cross}).
On Windows \verb|bmake test| runs for Cygwin output: the test programs
find their DLLs on \verb|PATH|. For mingw-w64 and MSVC output it stops
before building and says why --- the ATF that Kyua runs with on Windows
is a Cygwin library, which native programs cannot
link\reqfoot{REQ-test-windows-dll-paths-req}.

%===============================================================
\chapter{Linting}
\label{ch:linting}
%===============================================================

\texttt{Bmake It} manages compiler warnings itself and leaves static
analysis to the tools made for it, fed from the same build. This
chapter shows both.

\section{Warnings}

Every module compiles with \verb|-Wall -Wextra| (\verb|/W4| under
MSVC)\reqfoot{REQ-warn-macro-req}. Third-party code is kept quiet in two
ways, so that what remains are the project's own warnings:
\begin{lstlisting}[language=bmake]
# a module compiling vendored sources: no warnings from it
WARN=none

# a third-party framework: its public headers reach its users with
# -isystem, so they do not warn in the users' compiles either
PUBLIC_HEADERS_SYSTEM=yes
\end{lstlisting}
OpenRider's dependency framework sets \verb|PUBLIC_HEADERS_SYSTEM=yes|
and its compiled third-party modules \verb|WARN=none|. To make warnings
errors in the project's own code, add the flag in a hook file
(Section~\ref{sec:hooks}) of the project's framework, which leaves the
vendored framework alone:
\begin{lstlisting}[language=bmake]
# OpenRider/mk/pre.mk  (the framework's hooks, not the workspace's)
CFLAGS   += -Werror
CXXFLAGS += -Werror
\end{lstlisting}
Changing flags rebuilds the objects they affect: the build records its
inputs and recompiles when they change.

\section{Documentation Coverage}

\verb|DOC_WARN_IF_UNDOCUMENTED=YES| in a framework makes
\verb|bmake docs| report every undocumented entity of its public (and
\verb|DOC_INPUT_EXTRA|) headers --- a lint for the documented
interface. OpenRider sets it on its own framework.

\section{Static Analysis: clang-tidy, cppcheck}

\texttt{Bmake It} has no lint target; analysers read a \emph{compilation
database} (\verb|compile_commands.json|) recording each file's exact
compile command, which a recording tool writes during an ordinary build.
With Bear:
\begin{lstlisting}[language=bash]
$ bmake clean && bear -- bmake          # writes compile_commands.json
$ run-clang-tidy -p . OpenRider/        # clang-tidy, with the project's .clang-tidy
$ cppcheck --project=compile_commands.json --enable=warning,style
\end{lstlisting}
OpenRider keeps its naming rules in a \verb|.clang-tidy| at the
workspace root and ignores \verb|compile_commands.json| in version
control; its header filter limits the checks to the project's own
headers, so third-party code is not analysed. Record the database per
target key: a cross build's commands carry the target's flags and
sysroot.

\section{Sanitizers as Run-Time Lint}

Sanitizers find what static analysis misses --- out-of-bounds accesses,
use after free, undefined behaviour, data races --- while the tests run:
\verb|bmake test SANITIZE=address,undefined| (Chapter~\ref{ch:testing}).
A periodic sanitizing run can keep its own dashboard with
\verb|TEST_REPORT_DIR=test-report-sanitized|.

%===============================================================
\chapter{Profiling}
\label{ch:profiling}
%===============================================================

\texttt{Bmake It} has no profiling target of its own. A profiler is
either a program run around yours --- which \verb|bmake run| does with
the right libraries found --- or compiler instrumentation, which is
a matter of flags, best switched on with a variable of the project's
own in a hook file. Performance can also be held as a test.

\section{Sampling Profilers}

\begin{lstlisting}[language=bash]
$ bmake run PROGRAM=perf ARGS="record -g openrider --snapshot out.png"   # Linux
$ bmake run PROGRAM=perf ARGS="report"
$ bmake run PROGRAM=valgrind ARGS="--tool=callgrind openrider"         # Linux, FreeBSD
$ bmake run PROGRAM=bash        # then: dtrace, pmcstat, xctrace ... by hand
\end{lstlisting}
Build with symbols (\verb|DEBUG_FLAGS=-g|) and optimisations, so the
profile shows the code you ship with readable names. Keep frame
pointers for call graphs with \verb|-fno-omit-frame-pointer|.

\section{Instrumented Builds: gprof and Coverage}

Instrumentation changes compile and link flags for every module. Give
the project a switch in its workspace hook file, so one command line
turns it on everywhere and another target key's build is not affected
by mistake:
\begin{lstlisting}[language=bmake]
# mk/pre.mk (the workspace's)
.if ${PROFILE:U} == "gprof"
CFLAGS   += -pg
CXXFLAGS += -pg
LDFLAGS  += -pg
.elif ${PROFILE:U} == "coverage"
CFLAGS   += --coverage -O0
CXXFLAGS += --coverage -O0
LDFLAGS  += --coverage
.endif
\end{lstlisting}
\begin{lstlisting}[language=bash]
$ bmake PROFILE=gprof TOOLCHAIN=gcc && bmake run PROGRAM=openrider
$ gprof build/linux-amd64-gcc/bin/openrider gmon.out | less
$ bmake test PROFILE=coverage && gcovr -r .         # coverage of the test suite
\end{lstlisting}
\verb|PROFILE| is the project's variable, not \texttt{Bmake It}'s; a
command-line variable reaches every framework and module of the run.
The build records its flags, so switching \verb|PROFILE| on and off
rebuilds what it affects. Do not add these flags to \verb|CFLAGS| on
the command line itself: a command-line \verb|CFLAGS| replaces the
makefiles' value instead of adding to it.

\section{Performance as a Test}

OpenRider keeps its hot paths --- reprojection, track drawing, tile
warping --- in a \verb|perf.tst| test module. Each measurement is
divided by the time of a fixed calibration workload run on the same
machine, and must stay within a budget of three to ten times the ratio
measured when it was set, so the budgets hold on any host, emulated or
not, and only a gross regression fails. Every figure is printed, so
\verb|kyua report --verbose| shows the trend:
\begin{lstlisting}[language=bash]
$ bmake test FW=OpenRider TEST=perf_test
$ kyua report --verbose | grep -A20 perf_test
\end{lstlisting}

%===============================================================
\chapter{Tutorial: Building \texttt{System} and \texttt{Hello} From Scratch}
%===============================================================

This tutorial builds the same worked example used throughout the
design documents: two frameworks, \texttt{System} (no dependencies)
and \texttt{Hello} (depends on \texttt{System}), where \texttt{Hello}
contains an executable module \texttt{hello.m} and a shared-library
module \texttt{libgreet.m} that \texttt{hello.m} links
against\reqfoot{REQ-framework-contains-modules}.

\section{Step 1 --- Create the Workspace}

\begin{lstlisting}[language=bash]
$ mkdir -p myworkspace
$ cd myworkspace
$ cat > makefile <<'EOF'
.include <mk.workspace.mk>
PARENT_WS=
EOF
\end{lstlisting}

An empty \verb|PARENT_WS=| is valid — this workspace has no parents.

\section{Step 2 --- Create the \texttt{System} Framework}

\begin{lstlisting}[language=bash]
$ mkdir -p System/include System/local/include
$ cat > System/makefile <<'EOF'
.include <mk.framework.mk>
PREREQS=
EOF
\end{lstlisting}

The empty, but present, \verb|PREREQS=| is what makes \texttt{System}
auto-discoverable as a framework at all\reqfoot{REQ-prereqs-mandatory-even-empty-req}.

\section{Step 3 --- Create the \texttt{Hello} Framework}

\begin{lstlisting}[language=bash]
$ mkdir -p Hello/include Hello/local/include
$ cat > Hello/makefile <<'EOF'
.include <mk.framework.mk>
PREREQS=System
EOF
\end{lstlisting}

\section{Step 4 --- Create the \texttt{libgreet.m} Library Module}

\begin{lstlisting}[language=bash]
$ mkdir -p Hello/libgreet.m/src Hello/libgreet.m/include
$ cat > Hello/libgreet.m/makefile <<'EOF'
.include <mk.lib.mk>
LIB=greet
LIB_SHARED=YES
SHLIB_MAJOR=1
LIBS=
EOF
$ cat > Hello/libgreet.m/include/greet.h <<'EOF'
void greet(void);
EOF
$ cat > Hello/libgreet.m/src/greet.c <<'EOF'
#include "greet.h"
#include <stdio.h>
void greet(void) { printf("hello from libgreet\n"); }
EOF
\end{lstlisting}

Note \verb|greet.h| lives in the module's own \emph{private}
\verb|include/| — visible only to \verb|libgreet.m|'s own sources, not
even to sibling module \verb|hello.m|, regardless of the fact that
\verb|hello.m| will link against
it\reqfoot{REQ-three-level-header-visibility-req, REQ-libs-macro-link-only-headers-via-prereqs-req}.
If \texttt{hello.m} needed to \verb|#include "greet.h"| directly, it
would need to live in \texttt{Hello}'s \verb|local/include/| instead.

\section{Step 5 --- Create the \texttt{hello.m} Executable Module}

\begin{lstlisting}[language=bash]
$ mkdir -p Hello/hello.m/src
$ cat > Hello/hello.m/makefile <<'EOF'
.include <mk.prog.mk>
PROG=hello
LIBS=greet
EOF
$ cat > Hello/hello.m/src/main.c <<'EOF'
extern void greet(void);
int main(void) { greet(); return 0; }
EOF
\end{lstlisting}

\section{Step 6 --- Build}

\begin{lstlisting}[language=bash]
$ cd Hello
$ make
\end{lstlisting}

Behind the scenes: \verb|libgreet.m| is built first (it has no
dependency on \verb|hello.m|), producing \verb|libgreet.so.1| with a
\verb|libgreet.so| symlink; \verb|hello.m| is built second, since its
\verb|LIBS=greet| entry makes it depend on \verb|libgreet.m| having
been \emph{fully} built first\reqfoot{REQ-fused-build-per-module-full-dependency-order-req}.
Both modules' artifacts are then copied up into
\verb|Hello/build/<KEY>/{bin,lib}/|\reqfoot{REQ-aggregation-step-copies-outputs}.

\section{Step 7 --- Run It}

\begin{lstlisting}[language=bash]
$ cd ..    # back to the workspace root
$ make run PROGRAM=hello
hello from libgreet
\end{lstlisting}

\verb|make run| sets \verb|LD_LIBRARY_PATH| (or
\verb|DYLD_LIBRARY_PATH| on macOS) to include the workspace's
consolidated \verb|build/<KEY>/lib/| before executing, so
\verb|libgreet.so| is found without needing a real \verb|make install|
step first\reqfoot{REQ-run-target-req}.

\section{Step 8 --- Clean Up}

\begin{lstlisting}[language=bash]
$ make clean TARGET=all
\end{lstlisting}

This removes every generated artifact for every target present — the
whole \verb|build/| tree, any \verb|distrib/| packaging staging, and
all internal caches — leaving the workspace indistinguishable from a
fresh checkout\reqfoot{REQ-clean-removes-all-derived-artifacts-req}.
