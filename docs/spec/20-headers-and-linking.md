# Bmake It — 20: Header & Library Resolution

Status: DRAFT, synthesized from confirmed `project-model/req/` objects.

## Three-level header visibility

Supersedes an earlier two-level design; deliberately *not* real `mkmk`'s
four-level Public/Protected/Private/Local scheme, which was rejected
outright (`NREQ-no-four-level-header-visibility`) — no "Protected" level,
no enforced include-direction checks.

| Level | Directory | Visible to |
|---|---|---|
| Public | `fw/include/` | Any framework that declares this one in its `PREREQS=` |
| Framework-internal | `fw/local/include/` | All of this framework's own modules |
| Module-private | `module.m/include/` | Only that module's own source files — not even sibling modules |

(`REQ-three-level-header-visibility-req`)

## Where headers actually come from

| What | Resolved from |
|---|---|
| Hand-written public headers | `fw/include/` (source, always) |
| Framework-internal headers | `fw/local/include/` (source) |
| Module-private hand-written headers | `module.m/include/` (source) |
| Generated headers, private (default) | `module/build/<KEY>/include/` |
| Generated headers, promoted public | `fw/build/<KEY>/include/` (generated-only; named via `INCL=`) |
| Libraries to link against | `fw/build/<KEY>/lib/` (compiled artifact — always build output) |
| Workspace-level `build/<KEY>/include/` | **Never exists / never consulted at compile time** — packaging/install only |

(`REQ-headers-resolved-from-source-req`, `REQ-generated-headers-in-build-tree-req`)

**Why headers are never read from `build/`** (except the one deliberate
exception below): headers are plain text, not compiled artifacts — they
don't need per-target staging the way `.o`/`.so` do. Staging them would
add an unnecessary copy step and a new ordering dependency (headers would
need staging to finish before anything downstream could even start
compiling). A workspace-wide consolidated `include/` would also be
actively wrong, not just unnecessary: it would flatten every framework's
public headers into one namespace, discarding which framework a header
came from — undermining the entire point of `PREREQS`-based visibility.

**The one exception — generated headers.** Headers generated by tooling
(lex/yacc, etc.) don't exist until the build runs, so they can't live in
`include/` as source:

- **Private by default**: a module's generated headers land in
  `module/build/<KEY>/include/`, visible only to that module's own
  compilation.
- **Promotion to public**: a module names specific generated headers via
  `INCL=<header1> <header2> ...` (`REQ-incl-macro-promotes-generated-headers-req`).
  On module build, those are copied up to `fw/build/<KEY>/include/` — a
  framework-level directory containing **only** generated headers, never
  hand-written ones.
- **Cross-framework lookup** for a `PREREQS`-declared framework searches
  **both** its `fw/include/` (hand-written) **and** its
  `fw/build/<KEY>/include/` (promoted generated) — the one deliberate,
  scoped exception to "never consult `build/` for headers."

## `LIBS=` is link-only

`LIBS=lib1 lib2 ...` (replacing an earlier `LINK_WITH=` design that was
dual-purpose) is **purely a link-time instruction**
(`REQ-libs-macro-link-only-headers-via-prereqs-req`). It has **no effect
whatsoever** on header visibility — not even for sibling modules in the
same framework. A module's private `include/` stays private regardless
of who links against it. Header visibility is driven **exclusively** by
the containing framework's `PREREQS=`.

## Build ordering implications

Because generated+promoted headers and linked libraries are both genuine
build *outputs* (not source), they impose real ordering constraints —
see `30-build-sequence.md` for the full picture. In short: whenever
module/framework X depends on Y for **either** a consumed promoted
header **or** a link-time library, Y must be **fully built** before X
starts, not just partially
(`REQ-fused-build-per-module-full-dependency-order-req`). Compiling a
module that depends only on hand-written headers has no such ordering
requirement at all.
